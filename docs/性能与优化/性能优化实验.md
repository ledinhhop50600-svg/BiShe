# 内存与模型调用速度优化实验

- 日期：2026-10-29
- 环境：Windows 11 / JDK 17 / MySQL 8.0.46 / Python 3.11 / Node 22，前后端、智能体与数据库同机运行
- 模型：DeepSeek `deepseek-flash`，关闭思考（`REASONING_EFFORT=none`）
- 目的：在不牺牲审核与适配质量的前提下，回答两个问题——**内存能不能降、速度能不能快**，并把代价写清楚

## 结论先行

| 指标 | 优化前 | 优化后 | 说明 |
|---|---|---|---|
| 后端应用 JVM（RSS） | 209.2 MB | 152.6–172.9 MB | 小堆 + 串行 GC + 收窄线程池；堆 37 MB、Metaspace 49.5 MB、31 线程 |
| 后端启动方式（RSS） | Maven 模式：应用之外还有父进程 | Maven 模式 173.0 + 256.5 = **429.5 MB**；jar 模式 **184.8–204.3 MB** | `mvn spring-boot:run` 的隐藏开销；打包后没有 Maven 父进程 |
| 前端常驻（RSS） | 222.4 MB（Vite dev） | **98.1 MB**（production preview） | 降约 56%；真正的静态托管还可以完全不跑 Node |
| MySQL（Private） | 664.4 MB | 未改（需全局配置 + 重启） | 其中 `performance_schema` 约 231 MB、Buffer Pool 约 131 MB；本机多个库共用该实例，没有擅自改 |
| 智能体（RSS） | 75.1 MB | 75.1 MB | 不加载本地模型，依赖已经很少，继续压的空间只有几 MB |
| 三平台适配（短文） | 12.7 s（串行） | **6.1 s**（并行） | 生产接口复测 4.4–4.8 s；长文 21.8 s → 9.6 s |
| 单次预检 / 正式初审 | 3.2 s / 4.5 s | 不变 | 模型调用占 98% 以上，优化重点不在数据库 |
| 思考强度 | low / high 约 8.5 s | **none 5.6 s / 608 token** | 判定等级相同，开思考没有看到质量收益 |

一句话：**内存能降的是“开发期工具”和“后端启动方式”，MySQL 要动全局配置；速度上唯一稳定的大收益是按平台并行，关思考是正确的默认，分平台提示词是质量手段而不是速度手段。**

## 一、测量口径

- RSS / Private 来自 Windows `Get-Process`；RSS 含共享页，进程相加会略大于真实独占内存。
- JVM 堆、Metaspace、线程数来自 `jstat -gc` 与 `jcmd`；MySQL 的构成来自 `performance_schema.memory_summary_global_by_event_name`。
- 耗时取 2–3 次的中位数；模型耗时受网络与服务端排队影响，只代表测量时段。
- Vite dev 与 preview 是二选一，不能相加；报告中的合计按 dev 计入，preview 单独给出。
- `mvn spring-boot:run` 会同时留下应用 JVM 和 Maven 父进程；性能脚本按端口识别应用 JVM，父进程不计入合计，本报告单独列出。

## 二、内存：四个方向逐一试

### 2.1 前端：把开发服务器换成生产构建

Vite dev 常驻要负责模块转换、依赖预构建和 HMR，内存明显高于“把构建好的静态文件发出去”。

| 模式 | RSS | Private | 说明 |
|---|---|---|---|
| Vite dev（5173） | 222.4 MB | 1445.3 MB | 开发期使用；Private 主要是 Node 预留地址空间，看 RSS 更实际 |
| Vite preview（4173） | 98.1 MB | 114.9 MB | 先 `npm run build`，再由 preview 托管 `dist/` |

RSS 从 222.4 MB 降到 98.1 MB，约 **56%**。做法：

```bash
cd frontend
npm run build
npm run preview
```

`vite.config.js` 给 preview 配了 `/api` 代理到 8080，所以登录、看板、审核这些接口照常工作。代价是**没有热更新**，改完前端要重新 build；开发时仍用 `npm run dev`，演示/答辩时用 preview。

> 如果以后上 Nginx 或把 `dist/` 交给后端托管，连这 98 MB 的 Node 进程也不需要；本项目为了本地一键演示，保留了 preview。

### 2.2 后端：小堆 + 收窄线程池，以及去掉 Maven 父进程

原来的启动方式没有限制 JVM，Tomcat 默认最大 200 线程、Hikari 默认 10 连接，空载也有 59 个线程、209.2 MB RSS。改动：

```text
-Xms64m -Xmx256m -Xss512k -XX:MaxMetaspaceSize=128m -XX:+UseSerialGC
server.tomcat.threads.max=20
server.tomcat.threads.min-spare=5
spring.datasource.hikari.maximum-pool-size=5
spring.datasource.hikari.minimum-idle=2
```

同时关闭了 MyBatis 的默认 SQL 控制台日志（排查时再打开）。结果：

| 指标 | 调整前 | 调整后 |
|---|---|---|
| RSS | 209.2 MB | 152.6–172.9 MB |
| Private | 269 MB | 181.1 MB |
| 线程数 | 59 | 31 |
| JVM 堆 | 约 40 MB | 37.0 MB（已提交 64.1 MB） |
| Metaspace | 约 50 MB | 49.5 MB |

**一个容易被漏掉的点**：`mvn spring-boot:run` 不只是一个 JVM。它自己是一个 Maven 进程（本次实测 **256.5 MB RSS / 403.3 MB Private / 33 线程**），应用是它 fork 出来的子 JVM（173.0 MB）。也就是说开发启动的实际后端内存约 **429.5 MB**，比应用本身大一倍多。

打包后直接跑 jar，Maven 父进程就不存在了：

```bash
cd backend
mvn -DskipTests package
java -Xms64m -Xmx256m -Xss512k -XX:MaxMetaspaceSize=128m -XX:+UseSerialGC \
  -jar target/backend-0.0.1-SNAPSHOT.jar
```

实测 jar 进程 **184.8–204.3 MB RSS / 193.4–212.8 MB Private / 34–35 线程**（登录并加载菜单后），比“Maven + 应用”少约 **225–245 MB**。`backend/start-low-memory.bat` 已改为**优先运行已打包的 jar**，没有 jar 时才退回 `mvn spring-boot:run` 并提示先打包；它也会丢弃指向旧路径的 `JAVA_HOME`，回退到本机 JDK 17。

代价与边界：

- `-Xmx256m` 对单用户演示足够，但并发请求多时会更频繁 GC；不是生产容量建议。
- Serial GC 适合单机小堆，换成多核高并发场景应改回 G1。
- Tomcat 20 / Hikari 5 是“演示够用”的值；多人同时用要往上调。
- `-Xss512k` 对当前代码安全，但深递归场景要谨慎；Metaspace 128 MB 对 49.5 MB 的实际用量有余量。
- jar 模式不会自动重新编译；改完后端代码后要重新 `mvn -DskipTests package`。

### 2.3 MySQL：真正的大头是 performance_schema，不是 Buffer Pool

MySQL 的 WorkingSet（RSS）只有 44.2 MB，但 Private 是 **664.4 MB**，必须看 Private。用 `performance_schema` 的内存视图拆开：

| 组成 | 约占用 |
|---|---|
| `performance_schema` 合计 | **230.9 MB** |
| InnoDB Buffer Pool | 130.8 MB |
| InnoDB link buffer | 24.0 MB |
| InnoDB log buffer | 16.0 MB |
| 其余（连接、线程栈、分配器开销等） | 约 262 MB |

本项目的 `zimeiti` 库只有 **0.8 MB** 数据，128 MB Buffer Pool 远远用不满；但 `performance_schema` 默认开着，监控表自己就占了 231 MB，比 Buffer Pool 还大。

**尝试与限制**：

- 以 root 执行 `SET GLOBAL innodb_buffer_pool_size=67108864`（64 MB），值仍然是 128 MB。原因是 `innodb_buffer_pool_chunk_size=128M`，Buffer Pool 必须是“chunk × instances”的整数倍，64 MB 被向上取整回 128 MB；而 chunk size 是只读变量，动态改不了（`ERROR 1238`）。
- `performance_schema` 只能在启动时关闭，运行中不能靠 `SET GLOBAL` 释放。
- 这台实例上还有 `fastapi_first`、`self_media_platform`、`test`、`zxl` 等库，改的是全局配置并需要重启服务，所以本轮**没有擅自修改**，只给出可复现的方案。

如果确认这台机器只用于本项目的演示，可以在 `C:\ProgramData\MySQL\MySQL Server 8.0\my.ini` 的 `[mysqld]` 下加：

```ini
innodb_buffer_pool_size=64M
innodb_buffer_pool_chunk_size=16M
performance_schema=OFF
```

然后重启服务：

```bat
net stop MySQL80
net start MySQL80
```

预期 Private 从 664.4 MB 降到 **约 370–430 MB**（省 230–290 MB）。代价：

- `performance_schema` 关闭后，`sys` 库的性能视图、细粒度 SQL 统计不可用；做数据库性能排查时要再打开。
- Buffer Pool 64 MB 对 0.8 MB 的演示库足够，但同一实例上的其他库如果数据量变大，需要重新评估。
- 这是全局配置，会影响这台 MySQL 上的所有库；如果不想动全局，只改 Buffer Pool（保留 performance_schema）大约只能省 64 MB。

### 2.4 智能体：已经很轻，继续压的收益很小

智能体常驻 **75.1 MB RSS / 61.1 MB Private**，组成是 Python 解释器、FastAPI/uvicorn、openai SDK 和项目代码；它**不加载本地大模型**，向量化走免费的 bge-m3 API，所以没有 PyTorch/Transformers 那类几百 MB 的依赖。

`requirements.txt` 只有 5 个包：`fastapi`、`uvicorn[standard]`、`openai`、`pydantic-settings`、`python-dotenv`，没有可以砍掉的大件。把 `openai` 改成惰性导入只会把加载推迟到第一次请求，稳态内存不变，最多省几 MB；单 worker 已经是当前配置。**结论：这个方向不做改动**，75 MB 对一台 16 GB 的机器不是瓶颈。

### 2.5 合计怎么读

| 口径 | RSS | 校正后（MySQL 按 Private 计） |
|---|---|---|
| 开发模式（后端 Maven + Vite dev + Agent + MySQL） | 771.1 MB | 1391.3 MB |
| 应用 JVM 单独（不含 Maven 父进程） | 514.6 MB | 1134.8 MB |
| 演示模式（jar + preview + Agent + MySQL） | 421.7 MB | 1041.9 MB |

> 开发模式合计 = 应用 172.9 + Maven 256.5 + Agent 75.1 + Vite dev 222.4 + MySQL 44.2 = 771.1 MB；校正后把 MySQL 的 44.2 换成 664.4。演示模式 = jar 204.3 + Agent 75.1 + preview 98.1 + MySQL 44.2 = 421.7 MB。RSS 含共享页，合计只用于横向比较。

最有效的两步是：**前端 dev → preview（省 124 MB）**、**后端 Maven → jar（省 225 MB）**；MySQL 的 230 MB 是下一个大目标，但需要改全局配置并重启。

## 三、速度：时间到底花在哪

### 3.1 模型调用占 98% 以上

| 场景 | 总耗时 | 智能体 | 模型 | 后端/网络 |
|---|---|---|---|---|
| 登录（BCrypt + DB） | 134 ms | - | - | 全部 |
| 稿件列表（DB） | 108 ms | - | - | 全部 |
| 看板聚合 | 59 ms | - | - | 全部 |
| 智能体预检 | 3183 ms | 3120 ms | 3120 ms | 63 ms |
| 正式初审 | 4516 ms | 4456 ms | 4455 ms | 61 ms |
| 适配 1 平台 | 2884 ms | 2836 ms | 改写 1693 + 合规 1143 | 48 ms |
| 适配 3 平台（并行） | 4816 ms | 4741 ms | 三平台并行；另一次复测 4388 ms / 4216 ms | 75 ms |

检索/定位在缓存命中时接近 0 ms，数据库接口是几十到一百多毫秒。**换数据库、加索引不会让审核快多少；要快只能减少模型往返、减少输出 token，或者把多个平台并发起来。**

### 3.2 适配策略：并行是唯一“确定更快且不降质量”的方案

控制变量：同一篇短文（201 字）与长文（2102 字），三平台，每个平台一次改写 + 一次合规预检。

| 策略 | 短文总耗时 | 格式 | 形态特征 | 长文总耗时 | 长文格式 |
|---|---|---|---|---|---|
| 分平台 · 串行（原方案） | 12738 ms | 3/3 | 3/3 | 21784 ms | 3/3 |
| **分平台 · 并行（当前默认）** | **6136 ms** | **3/3** | **3/3** | **9637 ms** | **3/3** |
| 合并一次调用 | 9420 ms | 3/3 | 2/3 | 17773 ms | 2/3 |
| 通用提示词 · 并行 | 5717 ms | 3/3 | 2/3 | - | - |

- **并行**：短文快约 52%，长文快约 56%，格式与形态都不变。实现是 `ThreadPoolExecutor(max_workers=min(4, 平台数))`，每个平台独立走“改写 → 清理 → 格式自检 → 合规预检”；响应里保留 `adaptMs` / `complianceMs` / `durationMs`，方便定位慢平台。
- **合并一次调用**：改写从 3 次变 1 次，但单次输出变长，短文反而比并行慢（9.4 s vs 6.1 s），长文格式只有 2/3。少调用不等于快。
- **通用提示词**：只比并行快约 0.4 s，但形态特征从 3/3 降到 2/3。分平台提示词的价值是“像那个平台”，不是速度。

代价：并行会同时占用 3 个模型请求，遇到服务端限流时更容易触发 429；当前实现里任一平台失败会让整个请求失败，没有做“部分成功”。平台多、并发高时要把 `max_workers` 和重试策略一起考虑。

### 3.3 思考强度：关掉是正确默认

同一段违规文案，只改 `reasoningEffort`：

| 强度 | 总耗时 | 输出 token | 判定等级 | 命中规则 | 违规片段 |
|---|---|---|---|---|---|
| **none** | **5626 ms** | **608** | 2 | 5 | 7 |
| low | 8476 ms | 1136 | 2 | 6 | 6 |
| high | 8578 ms | 1117 | 2 | 6 | 7 |

适配侧同样：

| 强度 | 总耗时 | 输出 token | 格式 |
|---|---|---|---|
| none | 5313 ms | 359 | 1/1 |
| high | 7160 ms | 665 | 1/1 |

开思考的代价是**约 50% 的等待时间和接近 2 倍的输出 token**；在这类“按规则判定”的任务上，等级没有变好，命中规则/片段只有轻微差异。更实际的风险是长文时推理把输出预算耗尽，正文为空（阶段 5 实测过），所以生产默认 `none`。

> low/high 谁更快会受服务端排队影响，样本只有 2 轮；“none 明显最快、token 最少”在审核和适配两组里都成立。如果以后要做多步推理（例如先定位再解释），可以按场景临时打开，并同步提高 `max_tokens`。

## 五、没有采用或没有改的

- **MySQL 全局调参**：需要改 `my.ini` 并重启，且影响同实例上的其他库；本轮只做了根因拆解和命令级方案，没有落地。
- **智能体惰性导入/换框架**：75 MB 已经接近“Python + FastAPI + SDK”的合理下限，收益只有几 MB。
- **统一改写作为默认**：更慢且长文格式不稳，保留为实验开关。
- **通用提示词作为默认**：略快但丢失平台形态，保留为实验开关。
- **开思考作为默认**：更慢、token 更多，规则判定没有看到质量收益。
- **本地小模型/量化**：RTX 3050 4 GB 跑不动可用模型，仍然走云 API；离线演示用回放缓存。

## 六、复现

```bash
# 1) 生产式前端
cd frontend
npm run build
npm run preview          # http://localhost:4173

# 2) 后端：推荐 jar（无 Maven 父进程）
cd ../backend
mvn -DskipTests package
java -Xms64m -Xmx256m -Xss512k -XX:MaxMetaspaceSize=128m -XX:+UseSerialGC \
  -jar target/backend-0.0.1-SNAPSHOT.jar

# 3) 智能体
cd ../agent
.venv\Scripts\python -m uvicorn main:app --port 8001

# 4) 内存/耗时与速度实验
python tools/perf_report.py
python tools/experiment_speed.py
```

`experiment_speed.py` 会真实调用模型（约 1–2 分钟、几角钱以内），结果写入 `docs/性能与优化/实验-速度优化.md`、`docs/perf/speed-experiment.json` 与两张图。脚本给每次请求生成独立 `requestId`，避免命中回放缓存导致“耗时比总耗时还长”的假数据。

## 七、答辩时可以怎么讲

1. **内存**：我先用数据把占用拆开，发现大头不是业务代码——是 Vite 开发服务器、Maven 父进程和 MySQL 的 `performance_schema`。前端改生产构建省 56%，后端改 jar 去掉 Maven 省 225 MB；MySQL 的 231 MB 需要全局配置和重启，我没有在共用实例上擅自改，而是给出了可复现的命令和代价。
2. **速度**：预检 98% 的时间在模型，所以优化的是模型调用方式。三平台从串行改并行，12.7 s 降到 6.1 s，质量和格式不变；合并成一次调用反而更慢，分平台提示词也不是为了快。
3. **代价**：并行更吃并发和限流，小堆在多人并发时会频繁 GC，关思考不适合复杂推理，MySQL 全局调参会牺牲监控。每个选择都有明确的适用边界，不是“参数越小越好”。
