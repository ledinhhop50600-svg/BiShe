## 一、项目概况

### 1.1 系统定位

本系统是**面向多平台的内容创作、适配与合规管理平台**，服务于两类使用者：

- **平台运营人员**：审核内容、管理用户与权限、维护审核规则与目标平台配置
- **内容创作者**：创作投稿、查看审核反馈、把同一份内容适配成不同平台所需的形态

系统包含三部分：前端界面（Vue）、后端主系统（SpringBoot）、**内容审核与跨平台适配智能体（Python 独立服务）**。智能体是本项目的创新点。

### 1.2 创新点说明

创新点是**一个单智能体**（不是多智能体），具备三项能力：

1. **平台内容审核**：按规则库分级判定稿件的风险等级（通过 / 疑似 / 违规 / 严重），输出判定理由、违规片段定位与处置建议
2. **按目标平台规则的合规预检**：同一篇内容发到不同平台，规则并不相同（例如站外引流在小红书属违规、在别的平台可能只是提示），智能体按目标平台分别检查
3. **跨平台内容适配**：把一篇内容自动改写成各平台所需的形态 —— 小红书（短标题 + 口语化 + 话题标签）、微博（140 字内 + 话题）、微信公众号（长文）、B站（标题 + 简介 + 标签）、抖音（口播脚本），并做格式约束自检

**重要边界（已调研并明确排除）**：系统**不对接真实第三方平台的发布接口**，不会把内容真正发布到公众号、小红书等平台。原因已完成调研：抖音发布权限不接受个人开发者申请（需企业资质）；微信发布接口对个人主体账号已被官方回收（官方文档明确 2025 年 7 月起）；小红书无公开接口且自动化发布封号风险最高；微博、知乎等接口仅面向企业认证用户。因此系统内**保留"目标平台"概念**，把价值落在**内容适配**与**合规预检**上——这两项不依赖任何平台接口，对创作者有实际用处。详细调研记录见项目文档 `docs/decisions-multiplatform.md`。

### 1.3 技术选型

| 层 | 选型 | 版本 |
|---|---|---|
| 后端框架 | Spring Boot | 4.1.1 |
| 运行环境 | JDK | 17 |
| 持久层 | MyBatis-Plus | 3.5.17 |
| 认证授权 | Sa-Token | 1.46.0 |
| 数据库 | MySQL | 8.0.46 |
| 前端 | Vue 3 + Vite + Element Plus + Pinia | 3.5 / 8.2 / 2.14 |
| 智能体服务 | Python + FastAPI + openai SDK | 3.11 / 0.143 / 3.31 |
| 大模型 | DeepSeek（deepseek-flash） | 按用量计费，实测约 0.4 分/次 |

**选型依据（简要）**：后端与前端按任务书要求使用 SpringBoot + Vue；持久层选 MyBatis-Plus 而非 JPA，是为了单表操作免写 SQL、复杂查询仍可控；权限框架选 Sa-Token 而非 Spring Security，是因为它的登录与鉴权语义更直观（一行代码登录、注解鉴权），便于说明与维护；智能体独立成 Python 服务，是因为大模型的工具生态与向量检索生态集中在 Python，且两者通过 HTTP 接口解耦——智能体故障时主系统可退回人工审核，不影响演示。

**成本**：大模型 API 月预算控制在 50 元以内（实测单篇审核约 0.4 分钱，100 条评测集跑一遍约 0.4 元）。向量检索使用免费的 bge-m3 模型。

## 二、已完成的工作

目前已从零搭建出一个**可运行、可演示的完整系统骨架与权限体系**，具体包括以下四块工作。

### 2.1 开发环境与工程骨架

- 搭建了后端（SpringBoot + Maven）、前端（Vue 3 + Vite）、智能体服务（Python + FastAPI）三套工程，并配好一键启动脚本 `start.bat`：双击即可自动检查数据库、按序启动三个服务并打开页面
- 解决了国内网络环境下的依赖下载问题（Maven 与 npm、pip 均配置国内镜像）
- **实测确认了技术栈可用性**：这一环节并非形式，实际发现了若干问题（例如脚手架生成的 Spring Boot 版本号 `4.1.1.RELEASE` 在仓库中并不存在、Boot 4 的 starter 名称与 Boot 3 不同、MySQL 命令行导入中文需显式指定字符集），在写业务代码之前就解决了，避免了后期返工

### 2.2 数据库设计

共设计 **16 张表**，按职责分为三组：

- **权限组（5 张）**：用户、角色、菜单（含按钮级权限）、用户-角色关联、角色-菜单关联
- **内容组（5 张）**：稿件、分类、标签、稿件标签关联、举报
- **审核与适配组（6 张）**：目标平台清单（含格式约束）、审核规则库（通用规则 + 平台专属规则）、审核记录、审核复核记录、敏感词库、适配记录

几处设计考虑：稿件采用"状态机"管理（草稿 / 待审核 / 已发布 / 已驳回 / 已阻断 / 已下架）；密码存储 BCrypt 加盐哈希，数据库中看不到明文；审核组的 6 张表**在内容管理之前就建好**，后期智能体接入时不需要改表结构，避免返工；稿件表里刻意准备了若干"文明但明显违规"的样本（如含"全网最低价 + 三天见效"的极限词样本、含"加我微信"的站外引流样本），供智能体上线后演示与评测使用。

### 2.3 登录认证

- 实现了登录、登出、获取当前用户三个接口，采用令牌机制：服务端签发令牌，前端保存并在后续请求中自动携带，服务端据此识别用户身份
- 密码校验采用"拿明文重新计算哈希再比对"，不可逆；账号不存在与密码错误返回同一提示，避免被用来试探系统中有哪些账号
- 前端实现了登录页、路由守卫（未登录自动跳登录页）与请求拦截器（登录失效自动清理状态）
- 提供三个演示账号（管理员 / 审核员 / 创作者），登录页可一键填入

### 2.4 权限管理（RBAC）与后台框架

- 完成了**用户管理**（增删改查、启用/禁用、重置密码）、**角色管理**（增删改、**分配菜单与按钮权限**）、**菜单管理**（树形菜单与按钮权限的维护）三个功能页面
- 后台主框架成型：左侧菜单 + 顶栏（面包屑、当前角色、退出登录）+ 内容区
- **权限体系设计为三层防线**：
  1. 前端路由守卫 —— 无权限的页面跳转到 403 页面
  2. 按钮权限指令 —— 无权限的按钮不渲染
  3. **后端接口权限注解 —— 真正的安全边界**：即使绕过前端直接调用接口，也会被拒绝（实测审核员与创作者调用管理接口 6 项全部返回 403）
- **菜单完全由数据库驱动**：前端没有写死任何一项菜单。管理员在"角色管理"中勾选权限 → 写入关联表 → 该角色用户重新登录后，菜单、可进入的页面、可点按钮同时变化，**全程不需要改代码、不需要重启服务**

## 三、关键技术点与难点

### 3.1 三种角色的权限差异（可现场演示）

| 账号 | 角色 | 登录后可见的菜单 | 权限项 |
|---|---|---|---|
| admin | 超级管理员 | 数据看板、内容管理、审核中心、平台管理、创作中心、系统管理、评测中心 | 19 |
| reviewer | 审核员 | 数据看板、内容管理（仅举报处理）、审核中心（审核工作台、审核记录） | 5 |
| creator | 创作者 | 数据看板、创作中心（我的稿件、去投稿、跨平台适配） | 4 |

**演示效果**：用创作者账号登录，左侧只有"数据看板"和"创作中心"；直接访问管理员页面的地址会被拦到 403 页面（见插图 `docs/assets/阶段2-越权被拦截403.png`）。

### 3.2 难点与解决（三个已解决的实质问题）

1. **权限回显可能造成数据丢失**：角色"分配权限"弹窗初版打开时，已有权限没有被勾选（界面全空）。这是**危险的缺陷**——管理员若直接保存，会把该角色权限全部清空。根因是 Element Plus 的权限树只在创建时读取"默认勾选"配置，复用同一棵树切换角色时不会更新。解决方式是每次打开弹窗时强制重建树，并实测确认回显与数据库记录精确一致。

2. **Windows 下批处理脚本的中文与换行符**：一键启动脚本最初双击后报错，服务无法启动。经排查是两个问题叠加：批处理文件必须用 CRLF 换行（用 LF 会导致命令行解析错位）、中文必须用系统 OEM 编码（GBK）保存，而不是常见的"UTF-8 + 文件内切换代码页"写法。已修正并测试通过。

3. **数据库中文乱码**：用命令行导入含中文的建表与种子脚本时，中文变乱码。原因是 Windows 上的 MySQL 客户端默认字符集不是 utf8mb4，导入时需显式指定（`--default-character-set=utf8mb4`）。已作为规范写入文档，后续脚本统一按此执行。

以上问题都已记录在分阶段的开发笔记中（`docs/notes/`），并附有解决办法与验证方法。

### 3.3 工程规范

- 每阶段产出**开发笔记**，固定包含"本阶段你必须能讲出来的 3 件事"（用于答辩准备）
- 采用 Git 做版本管理，每阶段结束留一个可回退的存档点
- 已建立文档体系：系统功能说明、数据库设计文档、技术栈说明、阶段划分、以及 4 份决策记录（记录技术选型的结论与理由）

### 4.1 可运行的系统

双击项目根目录的 `start.bat`，脚本会自动：检查数据库 → 启动后端（8080）、前端（5173）、智能体服务（8001）→ 等待就绪 → 打开浏览器页面。

### 4.2 演示路线（约 3 分钟）

1. **登录页**：展示三个演示账号（可一键填入）
2. **管理员视角**：数据看板（用户数、稿件数、待审核数、稿件状态分布）→ 系统管理（用户 / 角色 / 菜单三个页面）

5. **占位说明**：点击"内容管理""审核中心"等菜单，显示"该模块将在后续阶段实现"——菜单与权限已配置好，功能待开发

## 五、后续工作计划

已完成的三块（环境骨架、数据库与登录、权限体系）是系统的"地基"，学校要求的管理系统主体已完成过半。后续按以下顺序推进：

| 序号 | 内容 | 说明 |
|---|---|---|
| 1 | 内容管理 | 稿件增删改查、分类标签、创作者投稿页、举报处理、敏感词库（作为后续对比基线）；**并冻结智能体对外接口契约** |
| 2 | 智能体服务接入 | FastAPI 服务骨架、大模型接入与降级机制，先跑通"提交 → 返回结构化结论" |
| 3 | 审核智能体核心 | 规则库构建（按平台维度）、向量检索（RAG）、四级分级判定、违规片段定位与修改建议 |
| 4 | 跨平台内容适配 | 按目标平台生成适配版本、格式约束自检、适配后合规预检 |
| 5 | 人机协同闭环 | 审核工作台（采纳 / 改判 / 驳回，改判原因必填）、创作者端反馈与重新提交 |
| 6 | 评测与实验 | 构建评测集（公开数据集 + 自建样本 + 人工改判记录），完成"关键词规则 / 纯大模型 / RAG+大模型"三方案对比实验，以及适配效果评估 |
| 7 | 测试与交付 | 功能测试、文档整理、答辩准备 |

**进度说明**：前期工作占用了较多时间在"打地基"（环境验证、数据库设计、权限体系），这部分一次做扎实，后续业务模块的开发速度会明显加快。
