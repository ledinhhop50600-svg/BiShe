# 性能分析报告

- 生成时间：2026-10-29 11:28
- 环境：Windows 11 / JDK 17 / MySQL 8 / Python 3.11 / Node 22（前后端与 Agent 同机运行）
- 方式：先空载快照，再跑一轮代表性请求，最后再快照；耗时取 2-3 次的中位数。

## 一、内存占用

| 进程 | PID | RSS | Private | 说明 |
|---|---|---|---|---|
| 后端 SpringBoot | 94816 | 209.2 MB | 268.6 MB | JVM 堆 40.1 MB / 已提交 80.0 MB，Metaspace 49.8 MB，59 个线程 |
| 智能体 Python | 95060 | 74.2 MB | 58.3 MB | Python 解释器 + FastAPI/uvicorn + 模型 SDK；按请求处理，不加载本地大模型 |
| 前端 Vite | 25072 | 499.4 MB | 1434.6 MB | Vite 开发服务器；生产构建是静态文件，不需要 Node 常驻 |
| MySQL | 7180 | 34.7 MB | 662.5 MB | InnoDB Buffer Pool 128.0 MB + 连接/其他 |

**合计 RSS：约 817.5 MB**（RSS 含共享页，进程相加会略大于真实总量）。

> **怎么读这两个数**：MySQL 的 WorkingSet（RSS）只有 34.7 MB，但 Private 是 662.5 MB（Buffer Pool 128 MB + 连接/缓存），**以 Private 为准**；Vite 的 Private 1434.6 MB 是 Node 预留地址空间，RSS 499.4 MB 更接近实际，且生产构建是静态文件、不需要 Node 常驻。把 MySQL 的 Private 计入、Vite 只算 RSS 时，约 **1445.3 MB**。

## 三、结论

1. **耗时主要在模型调用**：预检的模型耗时 3084 ms，占总耗时 98%；检索只有 0 ms（规则向量有缓存时几乎为 0）。所以优化重点不是数据库，而是模型选择、输出长度与并发。
2. **适配是串行的**：3 个平台 = 3 次改写 + 3 次合规预检，耗时约为单平台的 3 倍；如果要更快，应按平台并行，而不是换更快的数据库。
3. **内存大头是 MySQL 与后端 JVM**：MySQL Private 662.5 MB（Buffer Pool 128 MB），后端 RSS 209.2 MB（堆 40.1 MB、Metaspace 49.8 MB，其余是线程栈、Code Cache、直接内存与 JVM 自身）；智能体只有 74.2 MB，因为它不加载本地模型；前端 499.4 MB 是 Vite 开发服务器，生产构建不需要 Node 常驻。按 RSS 合计 817.5 MB，按 MySQL Private 校正约 1445.3 MB。
4. **前端 Vite 的内存是开发期开销**：生产构建后是静态文件，不需要 Node 常驻；不要把它算进线上容量。

## 四、口径与局限

- RSS / Private 来自 Windows `Get-Process`，包含共享库；合计不是精确的独占内存。
- Java 堆数据来自 `jstat -gc`，Metaspace 与线程数来自 `jcmd`；Direct Buffer、Code Cache 计入 RSS 但未单列。
- 模型耗时受网络与服务端排队影响，单机单次测量只代表当前时段；本报告取中位数。
- 数据量是教学演示规模（十几篇稿件），数据库查询耗时不能外推到大数据量。
