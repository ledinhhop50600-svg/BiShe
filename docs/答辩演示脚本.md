# 答辩演示脚本（5-8 分钟）

> 目标：在有限时间里把"AI 真的在业务里干活"讲清楚。
> 原则：**先演示、后解释**；每一步点完停 1-2 秒，让评委看清结果，再说话。

## 一、演示前检查（提前 10 分钟）

- [ ] MySQL 已启动；双击 `start.bat`，确认后端/前端/Agent 三个窗口都在；
- [ ] 打开 `http://localhost:5173/`，用 `creator / 123456` 登录一次，确认能进；
- [ ] 确认 `agent/.env` 的 Key 有效、余额足够（演示用不到 1 元）；
- [ ] 确认没有"待审核"稿件是当前账号自己投的（避免自审被拒）；
- [ ] 如果想让演示数据干净：重新执行 `db/02_schema.sql` + `db/03_seed.sql`
      （**会清空新建账号/稿件**，演示账号恢复默认）；
- [ ] 浏览器只留一个标签页，缩放 100%；关闭无关窗口。

**保底方案**：现场网络/Key 出问题，把 `agent/.env` 的 `PROVIDER` 改成 `mock`，
重启 Agent 窗口。界面流程完全一样，只是判定变成关键词模拟、适配返回截断版本。
提前把这个改法记在纸上，不要现场找。

## 二、时间分配

| 时间 | 内容 |
|---|---|
| 0:00-0:30 | 开场：系统定位与三种角色 |
| 0:30-2:00 | 创作者投稿 + **发布前 AI 预检** |
| 2:00-3:30 | 提交 → 审核员 **AI 初审** → 采纳/改判 |
| 3:30-4:30 | 创作者看反馈 → 修改重提 → 旧结论过期 |
| 4:30-6:00 | **跨平台适配**（小红书/公众号/抖音） |
| 6:00-7:00 | 审核记录 + 数据看板（改判率） |
| 7:00-8:00 | 评测中心 + 收尾 |

## 三、逐段脚本

### 0:00-0:30 开场

> "这是一个面向多平台的内容创作与合规管理平台，有三种角色：创作者、审核员、管理员。
> 我的创新点不是加一个聊天框，而是让**单智能体真正参与两条业务链**：
> 内容审核和跨平台适配。下面用一条完整流程演示。"

### 0:30-2:00 创作者投稿 + AI 预检

操作：
1. `creator / 123456` 登录；
2. 创作中心 → 去投稿；
3. 标题、正文粘贴下面这段（提前复制好）：

```
标题：秋冬必入的面霜，全网最低价
正文：这款面霜是全网最低价，三天见效，国家级实验室研发。想要的姐妹加我微信，备注面霜，我发你链接。
```

4. 点 **「发布前检查」**，等 3-6 秒。

讲解要点（指着结果）：
> "它给了四级分级里的**违规**，不是笼统的'不合规'。理由里引用了三条规则：
> AD-002 价格承诺、FB-001 功效承诺、FB-003 资质造假；每条都定位到原文片段，
> 并给出具体改法。这个预检**不落库、不阻断发布**，只是给创作者的建议。
> 它和后面审核员用的规则、判定逻辑是同一套，所以不会出现'预检说通过、审核说违规'。"

### 2:00-3:30 提交 → 审核员 AI 初审

操作：
1. 创作者点「提交审核」；
2. 退出，`reviewer / 123456` 登录；
3. 审核中心 → 审核工作台 → 左侧选这篇稿件；
4. 点 **「运行初审」**，等 3-8 秒；
5. 页面显示：违规、命中规则、4 处片段、处置建议、token/耗时；处理结果自动预选"驳回"，
   关系显示"采纳智能体建议"；
6. 点「提交审核结果」（原因已填或现填一句）。

讲解要点：
> "这一步的结论会写进 `audit_record`，谁、什么时候、用的哪个模型、花了多少 token 都可追溯。
> 审核员不是被 AI 替代，而是**终审**：他可以采纳，也可以改判；改判必须写原因，
> 原因会作为下一轮补规则的标注数据。"

### 3:30-4:30 创作者看反馈 → 修改重提

操作：
1. 换回 `creator`；
2. 创作中心 → 我的稿件 → 这篇 → **「查看反馈」**；
3. 展示：审核意见 + 智能体初审 + 违规片段高亮 + 逐条修改建议 + "采纳（最终：违规）"；
4. 点「去修改」，把正文换成正常内容（提前复制）：

```
标题：周末去公园走了走
正文：周末去公园走了走，看到很多人在放风筝。春天的风不大不小，正好适合。回家路上买了两斤草莓，洗干净放在玻璃碗里，孩子一口气吃了半碗。普通的一天，记录下来。
```

5. 保存并重新提交。

讲解要点：
> "创作者改完重提后，上一轮的 AI 结论会通过**内容哈希**自动标记为过期，
> 审核员必须对修改后的内容重新初审 —— 不会拿旧结论审新内容。"

### 4:30-6:00 跨平台适配

操作：
1. 创作中心 → 跨平台适配；
2. 选一篇已发布稿件（如《小户型收纳的 5 个实用技巧》）；
3. 勾选 **小红书 + 微信公众号 + 抖音**；
4. 点「生成适配版本」，等 10-20 秒；
5. 指着三个卡片讲：
   - 小红书：标题 14 字、口语化 + emoji、5 个标签；
   - 公众号：长文、分段/小标题；
   - 抖音：【画面】/【口播】脚本；
   - 每张卡片都有"格式通过/合规通过"，格式是**程序算的**（字数/标签），
     合规复用审核规则；
   - 点「复制全文」，底部有历史版本（v1/v2…）。

讲解要点：
> "同一篇内容，三个平台的形态完全不同。人工逐个改写很费时，这是大模型擅长的；
> 但字数和标签是客观约束，交给模型不可靠，所以由程序校验，超限会明确警告。
> 结果不直接发布，而是生成可粘贴的成品 —— 因为个人开发者拿不到各平台发布接口。"

### 6:00-7:00 审核记录 + 数据看板

操作：
1. `admin / 123456` 登录；
2. 审核中心 → 审核记录：展示每次判定、人工处理（采纳/改判）、原因；
3. 数据看板：智能体审核次数、改判率、判定分布、人工处理分布。

讲解要点：
> "改判率的分母只算'有可用初判'的审核；AI 失败或没跑初审判人工，不算人和 AI 不一致。
> 这张表就是论文里人机协同效果的数据来源。"

### 7:00-8:00 评测中心 + 收尾

操作：
1. 评测中心 `/eval`：审核实验四方案表、分层准确率、适配评估、人工评分对比；
2. 不点"运行演示评测"（首次 2-3 分钟，答辩时间不够）；说明"平时可以一键跑，
   回放缓存下约 25 秒"。

收尾话术：
> "实验上，RAG 在严格口径下 85%，但放宽口径下 B 更高 —— 我在论文里没有只报一个数字，
> 而是说明排序取决于口径，并给出选 RAG 的三条与策略无关的理由：可审计、策略可调、
> 人工兜底下偏保守。系统的局限也写清楚了：不真实发布、只做文本、样本量有限。
> 我的结论是：**AI 的价值不是什么都判对，而是被放进一个有约束、可追溯、可纠正的流程里**。"

## 四、可能被追问的现场操作

| 评委问 | 现场怎么答/怎么做 |
|---|---|
| "换一个正常内容试试？" | 用上面的正常段落跑预检，应显示"通过"或"疑似" |
| "AI 不可用怎么办？" | 切 `PROVIDER=mock` 重启 Agent；或指审核记录里的 `agent-failed` 说明降级 |
| "规则从哪来？" | 管理员 → 审核规则库，展示每条规则的 `source` |
| "适配结果能改吗？" | 结果是可复制的成品；修改在平台侧完成，系统保留历史版本 |
| "为什么微博不是 140 字？" | 140 是信息流展示长度；2016 年起原创微博上限 2000 字 |
| "长文会不会截断？" | 小红书/抖音会压缩，超限会标"未通过"并给出问题；不会静默通过 |

## 五、演示禁忌

1. **不要现场跑完整审核实验**（10 分钟以上）；用评测中心的已有结果；
2. **不要点"运行演示评测"**，除非评委明确要求且时间充足（首次 2-3 分钟）；
3. 不要用"待审核"里自己账号投的稿件做审核演示（自审会被拒）；
4. 不要在没有 Key/网络时硬跑真实模型；提前准备 mock 切换；
5. 不要照读文档；每页只讲"它解决什么问题 + 结果说明什么"。
