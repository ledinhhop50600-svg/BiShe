# 待优化清单

> **用途**：记录使用中发现的问题、优化需求与需要决策的点。
> **为什么要记而不是马上改**：零散修改会反复打断主线开发，而且部分界面的形态会被后面的 Agent 阶段推翻。
> 先把问题收集齐、分类清楚，再决定"现在改 / 决策后再改 / 最后集中改"。
>
> **分类定义**
> - **A 阻塞与缺陷**：功能不可用、数据错误、演示会翻车 → 立即修
> - **B 功能与规则调整**：涉及产品决策，或会被后续阶段推翻 → 决策后再做
> - **C 体验优化**：视觉、文案、交互打磨 → 阶段 7 之后集中做一轮
>

## 二、已修复

### #3a 内容广场看不到正文 · A 类（2026-10-16）

- **改动**：每张卡片增加「查看全文」，弹窗展示完整正文、作者、分类、发布时间与标签，弹窗底部直接提供「举报这篇内容」。
- **理由**：只看标题和摘要无法判断内容是否值得举报；从弹窗直接举报，操作路径最短。

### #3b 审核员也具备创作能力 · B 类（2026-10-16）

- **改动**：给「审核员」角色授予创作中心菜单（我的稿件 / 去投稿 / 内容广场），并补一条利益冲突规则：
  **不能审核自己投稿的稿件**（后端拦截，提示"请由其他审核员处理"）。
- **理由**：现实中一个人可以同时是审核员和创作者；但必须隔离利益冲突，否则审核员可以自己放行自己的违规内容。
- **影响**：审核员的菜单从 7 项变为 11 项，权限从 5 项变为 8 项。需重新登录生效（菜单在登录时下发）。

### #3c 举报处理看不到被举报稿件正文 · A 类（2026-10-16）

- **改动**：举报列表中的稿件标题改为可点击 → 弹窗展示正文 + 敏感词检测结果，审核员据此判断举报是否成立。

### #4 数据看板按角色区分 · B 类（2026-10-16）

- **改动**：`/api/dashboard/stats` 按角色返回三套指标，并附 `scope` 字段：
  - **管理员（admin）**：用户总数、稿件总数、各状态稿件数（全站）
  - **审核员（reviewer）**：待审核稿件数、待处理举报数、今日新增投稿数（任务视角）
  - **创作者（creator）**：我的稿件数 + 我的草稿/待审/已发布/被驳回数（个人视角）
  - 前端按 `scope` 渲染不同卡片与分布表；审核员额外给一个直达审核工作台的入口，创作者给"去投稿/内容广场"入口。
- **理由**：创作者看到"用户总数 4"没有任何决策价值，且属于平台级数据、不应暴露。

### #1 审核员无法打开审核工作台 · A 类

- **现象**：审核员进入审核工作台时弹出"没有操作权限"，待审队列永远显示 0 篇。
- **根因**：工作台调用 `GET /api/article/page` 拉取待审列表，而该接口只声明了 `article:list`（管理员权限）。审核员的权限是 `dashboard:view / report:handle / audit:workbench / audit:record / audit:rejudge`，**没有 article:list**，因此被 403 拦下。
  稿件详情接口当时写成"article:list 或 audit:workbench 任一即可"，所以详情一直正常 —— **只有列表这一处漏了**。
- **证据**：审核员调用该接口返回 403「没有操作权限」；管理员调用返回 4 条待审。
- **修复**：接口权限改为 `article:list` 或 `audit:workbench` 任一即可。
- **反思**：这是"接口按页面划分权限"的典型疏漏 —— **一个接口被多个页面复用时，权限必须覆盖所有调用方**。今后新增共用接口要逐一核对调用方。

### #6 稿件管理列表的 ID 序号 · A 类

- **现象**：列表首列显示 13、17、21 这类不连续的编号，看起来像"数据库有历史数据残留"。
- **真相**：**不是数据问题**。显示的本来就是数据库主键 `id`；测试期间反复创建与删除稿件，自增 id 自然不连续。
- **修复**：首列改为显示"当前页第几条"（`(页码-1) × 每页条数 + 行号 + 1`），与分页联动。数据库 id 仍用于后端操作，界面不再暴露。

## 三、需要决策的问题

### D1（对应 #2）注册与个人账号管理

**参照主流平台的做法，建议如下。**

**注册（公开页面，无需登录）**

| 项 | 建议 |
|---|---|
| 填写项 | 账号、密码、确认密码、昵称、图形验证码 |
| 账号规则 | 3–20 位字母/数字/下划线；**注册后不可修改**（主流平台普遍如此） |
| 密码规则 | 至少 6 位；建议要求同时包含字母与数字 |
| 角色 | **注册一律分配「创作者」角色**。管理员、审核员只能由管理员创建 —— 否则任何人都能注册成审核员，这是必须堵住的漏洞 |
| 生效方式 | 注册后立即可用。本系统没有短信/邮件服务，不做手机号或邮箱验证（**文档中如实标注为简化**） |
| 验证码 | 建议做：后端生成简单算式（如 `3 + 7 = ?`），答案是随机会话值。成本很低，能体现"防刷"意识 |

**个人中心（所有登录用户可用）**

| 功能 | 说明 |
|---|---|
| 修改昵称 / 邮箱 / 手机号 | 常规资料维护 |
| 修改密码 | **必须输入原密码**（防止会话被盗后直接改密）；新密码不得与旧密码相同 |
| 账号名 | 不可修改 |
| 头像 | 可选。要做的话需要文件上传 + 本地存储目录，工作量比上面两项大，建议放 C 类 |

**明确不做的**（建议写进文档，避免答辩被追问时答不上来）：
- 手机号/邮箱验证：需要第三方短信与邮件服务，本期不接
- 找回密码：同上，没有验证渠道就无法安全找回；建议由管理员重置（现有功能已支持）
- 登录失败锁定：需要额外存储与逻辑，本地演示价值不大

### D3（对应 #5）已发布稿件的编辑策略

| 方案 | 行为 | 评价 |
|---|---|---|
| A 直接改 | 编辑即时生效，不重审 | 最省事，但等于已发布内容可以随时变成违规内容 —— 不建议 |

### D4（对应 #7）审核标准的放宽 · **阶段 5 动工前必须定案**

截图里《在家做的减脂餐，一周瘦十斤》被判违规。问题不在于"判错"，而在于**规则没有区分内容性质**：
广告法的严格标准适用于**商业广告**，而个人经验分享（没有卖货、没有交易引导）不应套用同一把尺子。

建议改为「**先判内容性质，再定严格度**」：

| 等级 | 判定条件（建议） |
|---|---|
| 通过（0） | 正常内容 |
| **疑似（1）** | 有夸大、绝对化表述，但**无商业推广、无交易引导、无违法引导** → 转人工，默认倾向通过 |
| 违规（2） | 有商业推广 / 带货 / 交易引导 **且** 含虚假承诺；或站外引流；或明显侵权 |
| 严重（3） | 违禁品交易；违法违规引导；极端有害内容 |

对应你的要求：「夸大其词但没有卖货、没有违法违纪引导」→ 落在**疑似**，人工看一眼默认通过，而不是直接驳回。

**这个策略要同时改三处**：
1. **规则库**：广告法类规则的 `suggested_level` 从「违规」降为「疑似」，并新增一条「商业推广属性」规则作为前置判断
2. **Agent 的判定逻辑（阶段 5）**：把"先判断是否具有商业属性"写进判定策略 —— 关键词匹配做不到、智能体擅长，**这是一个很好的答辩点**
3. **种子数据**：这篇稿件的驳回原因按新策略重写（它应属"疑似转人工"，或换成一个真正有售卖行为的违规样本）

### D4 实施记录（2026-10-16，阶段 5 首步）

实际落地的做法与上述"改三处"略有调整，记录原因：

- **规则库**：新增 `BIZ-001 商业推广属性判定（广告法适用前提）`（规则总数 21 条）。
  **没有**把广告法类规则的 `suggested_level` 从 2 改成 1 —— 因为"建议等级"表达的应是"该规则成立时的严重程度"，
  而"是否成立"取决于内容性质。若把等级降为 1，商业推广中的极限词也会被低估。
  改为：规则等级保持 2，**由 BIZ-001 + 提示词决定"是否适用"**。这个分工更清晰，也更好解释。
- **智能体提示词**：系统提示词加入「分级策略」段：先判商业属性 → 广告法类规则只对商业内容按建议等级判定 →
  个人分享类的夸大表述判「疑似」并说明"建议人工复核" → 站外引流 / 违禁品 / 侵权不放宽。
- **实测（真实模型 deepseek-flash）**：
  - 稿件 #6（商业推广：直播间、29.9 元、库存两百单）→ **违规（2）**，7 处片段；
    理由原文："该内容具有明显的商业推广属性……因此广告法和虚假宣传类规则均按建议等级判定，**不适用个人分享豁免**。"
  - 稿件 #8（个人分享：无售卖、无引流）→ **疑似（1）**，4 处片段；
    理由原文："正文没有商品链接、价格、优惠、库存、直播间等交易信息……**不具备商业推广属性**，
    按分级策略……属于个人经验分享。"
- **待办**：种子数据里稿件 #8 的"已驳回"状态与原因是**旧口径**下的历史数据。
  阶段 7 把 Agent 判定面板接进审核工作台时，一并把这条示例改成与新策略一致的样本。

  「发布前检查」+「保存并提交审核」。
- 编辑时清空旧风险等级（-1）与驳回原因；旧审核结论靠 `content_hash` 判定为过期。
- 验证：`tools/verify_account_revision.py` 全部通过（注册、验证码、资料、改密、
  发布 → 编辑 → 待审 → 广场消失 → 再审发布 → 下架 → 编辑重审）。
