# 工作方式决策记录

> 本文件记录「怎么做这个项目」上的决定与理由，按主题分文件维护。
> 主题划分：本文件（工作方式）、[decisions-agent.md](decisions-agent.md)（创新点与 Agent 设计）、decisions-stack.md（技术选型，待建）。
> 目录约定：`docs/` 存放过程文档（决策记录、阶段开发笔记、设计稿）；`技术说明文档/` 与 `项目说明文档/` 存放对外交付版本，后续把过程文档整理成型后再放进去。

## D-P1 追问强度：深挖

- **结论**：需求梳理阶段采用「深挖」强度 —— 主动寻找风险、遗漏与边界情况，而不只是补齐明显缺口。
- **理由**：项目跨数月并作为求职作品（Agent 应用开发方向）。最大风险不是「写不出来」，而是创新点做浅（答辩被问穿、面试官不认）与范围失控（什么都想要、什么都不完整）。这两类风险在开工前发现的返工成本最低。
- **日期**：2026-10-16

## D-P2 保留决策记录

- **结论**：每个决定追加「结论 + 理由」，按主题分文件写在 `docs/` 下，并单列待定问题。
- **理由**：（1）数月后仍需要知道为什么这样选，否则会反复推翻自己；（2）技术说明文档与毕业论文的「方案论证」类章节可直接取材，无需回忆。
- **日期**：2026-10-16

## D-P3 阶段划分按依赖顺序，不按时间排期

- **结论**：阶段划分只表达「依赖顺序」与「完成标准」，不绑定日历日期和工期估计。每阶段写清：入口条件、产出物、验收标准。
- **理由**：用户明确表示不会按时间逐阶段推进。绑定时间的计划会在实际推进中失效，并制造虚假进度压力。
- **补偿措施**（因为取消时间轴，必须补上防漂移机制）：
  1. 阶段之间用**硬依赖**表达，跳阶段必须满足入口条件 —— 例如数据模型未定就不要写审核逻辑，否则表结构一改全盘返工。
  2. 「文档即产出物」：每个阶段的开发笔记属于该阶段的验收条件，不写完不算完成，避免代码跑通了但文档烂尾。
  3. 保留两个**学校行政节点**作为外部锚点（开题提交、中期检查）—— 这些是学校定的，不随个人节奏走，需要时提前确认日期。
- **日期**：2026-10-16

## D-P4 分工边界：代码由 AI 全权编写，用户零 SpringBoot/Vue 基础

- **结论**：项目代码、文档、阶段开发笔记全部由 AI 编写。用户负责：注册 API 账号与密钥、与导师沟通、行政节点提交、答辩前理解系统。
- **用户现状（按做过的事记录，非自评）**：SpringBoot/Vue 从未接触；Python 有基础（学过 FastAPI）；MySQL 会基本增删改查；大模型 API 调用过但代码写得不多；Redis、Docker 不熟；Git 知道但不熟；无服务器。
- **风险与对策**（本项目最大的单点风险）：
  - 风险：答辩现场会被要求解释代码与架构。若作者讲不清，会被质疑"不是自己做的"，直接威胁毕业。
  - 对策：①系统设计避免过度工程，每处技术都必须能用一句白话解释；②每阶段开发笔记附「本阶段你必须能讲出来的 3 件事」；③Agent 部分完成后单独产出「答辩问答准备」（含高频问题答法）；④关键阶段让用户亲手跑一遍并复述流程，而不是只看结果。
- **日期**：2026-10-16

## D-P5 运行形态：仅本地运行

- **结论**：不做服务器部署，不引入 Docker、不引入 Redis。全部组件在用户本机（Windows）可一键启动。
- **理由**：用户硬约束是无服务器、本地演示；且对 Docker/Redis 完全不熟 —— 引入只会提高"跑不起来"的概率，不带来答辩或求职上的实质加分。
- **例外处理**：答辩演示环境已确认**联网**（用户自备电脑 + 手机热点），因此不需要"离线可用"作为硬约束。但仍在 Agent 侧保留「响应回放模式」作为**测试手段**：本地缓存模型响应，使回归测试不依赖网络、结果可重复、重复跑评测不烧 token。它是测试工具，不是答辩兜底方案。

## D-P6 学校交付物由 AI 产出

- **结论**：开题报告、毕业设计任务书、中期检查表由 AI 产出，标准是「完整真实、不求详尽」，用户在其上修改调整。「指导日志模板」由用户自己填写（记录与导师会议），本项目不碰。
- **备注**：任务书与开题报告含「进度安排」表格，属学校格式要求，按常规学期安排填写，与 D-P3「阶段不绑时间」不冲突（那是交学校的表格，不是我们的工作计划）。
