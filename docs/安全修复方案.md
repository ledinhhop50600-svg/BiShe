## 二、P0：账号生命周期与令牌失效

### S1 禁用/删除/重置密码后踢下线

**现状**

- `UserServiceImpl.updateStatus` 只改 `sys_user.status`，不调用 `StpUtil.kickout`。
- `delete` 只做逻辑删除，不踢令牌。
- `resetPassword` 只改密码，不踢令牌。
- `SaTokenConfig` 的拦截器只做 `StpUtil.checkLogin()`，不查用户状态。
- 实测：被禁用账号拿旧令牌仍能访问 `/api/auth/me`，还能新建稿件。

**改法**

1. 在 `UserServiceImpl` 三个入口加踢下线：
   ```java
   // updateStatus：status == 0 时
   StpUtil.kickout(id);
   // delete：逻辑删除前
   StpUtil.kickout(id);
   // resetPassword：改密后
   StpUtil.kickout(id);
   ```
2. `update` 中如果改了密码或角色，也踢下线（权限/凭据变了，旧会话不应继续）。
3. 在 `SaTokenConfig` 的拦截器里补用户状态检查：
   ```java
   StpUtil.checkLogin();
   long userId = StpUtil.getLoginIdAsLong();
   SysUser user = userMapper.selectById(userId);
   if (user == null || Integer.valueOf(0).equals(user.getStatus())) {
       StpUtil.logout();
       throw new NotLoginException("账号已禁用或删除", ...);
   }
   ```
   演示规模每请求一次主键查询可以接受；要省查询可在登录时把状态写进 Sa-Token Session，
   但禁用/删除必须同时清 Session，否则会引入“会话里还是旧状态”的新问题。
4. 拦截器抛出的异常要能被 `GlobalExceptionHandler` 转成 401；补一条集成测试确认。

**验收**

- 管理员禁用 `creator2` → 用 `creator2` 旧令牌请求 `/api/auth/me`、`POST /api/article` 都 401；
- 重新启用后重新登录，接口恢复；
- 管理员重置某用户密码 → 旧令牌 401；
- 删除用户 → 旧令牌 401；
- 正常用户、管理员自己的会话不受影响。

**预计**：0.5–1 天（含测试）

## 三、P0：令牌读取面收窄

### S2 禁止 Cookie / URL 读取令牌

**现状**

- 登录响应有 `Set-Cookie`，但没有 `HttpOnly` / `SameSite`；
- `/api/auth/me?satoken=...` 可以直接通过；
- 前端同时把令牌放 localStorage，并由 axios 放请求头。

**改法**

1. 在 Sa-Token 配置里只允许从请求头读取：
   - 关闭 Cookie 读取；
   - 关闭 request body / URL 参数读取；
   - 保留 header 读取和 header 写出。
   Sa-Token 1.46.0 的具体 setter 名称以依赖为准（`isReadCookie` / `isReadBody` / `isReadHeader`），
   配置后必须实测，而不是只看文档。
2. 如果仍需要 Cookie 方案（例如以后上 HTTPS 的生产部署），则改为
   `HttpOnly + Secure + SameSite=Lax` 的 Cookie，并补 CSRF 防护；不要在 localStorage 和 Cookie 里各放一份。
3. 前端保持只用 `Authorization`/`satoken` 请求头；不把令牌拼进 URL。
4. 验收时同时看响应头：登录响应不应再出现可被 JS 读取的 token Cookie。

**验收**

- `GET /api/auth/me?satoken=<有效令牌>` → 401；
- 带伪造 Cookie 但无 header → 401；
- 正常 header 请求 → 200；
- 登录响应 `Set-Cookie` 消失，或只保留 HttpOnly/SameSite 的安全 Cookie（二选一）。

**预计**：0.5 天

## 四、P1：权限一致性

### S4 让 `audit:rejudge` 真正生效

**现状**

- 种子菜单里有 `audit:rejudge`，但 `ArticleServiceImpl.review` 只用 `audit:workbench`；
- 在角色权限页取消“改判”勾选，实际仍能改判。

**改法**

1. 后端在判定为 `ReviewActions.OVERRIDE` 时检查：
   ```java
   if (reviewAction == ReviewActions.OVERRIDE
           && !StpUtil.hasPermission("audit:rejudge")) {
       throw new BizException(403, "没有改判权限");
   }
   ```
   注意：`StpUtil.hasPermission` 在无权限时返回 false；不要用会抛异常的 `checkPermission` 破坏已有错误提示。
2. 前端审核工作台：改判按钮加 `v-perm="'audit:rejudge'"`，无权限时禁用并给出原因。
3. 如果产品决定“审核员天然可以改判”，就删掉这个权限标识和菜单项，避免“看起来能配、实际没用”。

**验收**

- 给 reviewer 角色取消 `audit:rejudge`，重新登录 → 改判接口 403，采纳/通过仍可用；
- 勾选后 → 改判成功，记录 `audit_review.action=2`；
- 前端按钮与接口行为一致。

**预计**：0.5 天

### S5 防止管理员把自己锁死

**现状**

- `RoleServiceImpl.update` 直接覆盖角色菜单；
- 管理员可以取消自己角色的 `system:role`，保存后无法再进角色管理，只能改库。

**改法（两层）**

1. `RoleServiceImpl.update`：
   - 查出本次 `menuIds` 对应的菜单权限；
   - 如果目标角色当前分配给登录用户，且新权限里不再包含 `system:role`，拒绝并提示
     “不能移除自己的角色管理权限，请先由其他管理员操作”。
2. `UserServiceImpl` 的禁用/删除/改角色：
   - 统计“仍有 `system:role` 权限且状态正常的用户”；
   - 如果操作会让数量变成 0，拒绝。
3. 前端角色页保存前给出确认提示；后端才是最终边界。

**验收**

- 管理员编辑自己的角色，去掉 `system:role` → 400/403，权限不变；
- 有第二个管理员时可以调整第一个管理员；
- 禁止禁用/删除最后一个管理员。

**预计**：1 天

## 五、P1：输入长度与错误码

### S6 统一长度校验

**现状**

- 标签、分类、敏感词、平台、举报理由、改判原因等入口直接把字符串写库；
- 超过 `varchar` 长度时 MySQL 报错，被兜底成 500“系统繁忙”；
- 控制器多数已有 `@Valid`，但实体/DTO 上缺 `@Size`。

**改法**

1. 给实体/DTO 加 `@Size`（上限对齐数据库列）：
   - `BizTag.name` 30；
   - `BizCategory.name` 50；
   - `AuditSensitiveWord.word` 100、`category` 30；
   - `AuditPlatform.platformKey/platformName` 50、`tagRule` 200、`styleDesc` 500；
   - `BizReport.reason` 500、`handleRemark` 500；
   - `AuditReview.remark` 1000；
   - `BizArticle.title` 200、`summary` 500、`rejectReason` 1000；
   - `SysUser.username/nickname` 50、`email` 100、`phone` 20、`remark` 255；
   - `SysRole.roleName/roleKey` 50、`description` 255；
   - `SysMenu.menuName` 50、`path/component` 200、`perms` 100、`icon` 50。
2. 控制器已有 `@Valid` 的保持不变；没有 `@Valid` 的补上。
3. 举报/审核这类由服务层接收的字符串，在 service 里再兜一层 `StringUtils`/长度检查，
   返回 `BizException(400, "...最多 N 字")`。
4. 不要只在前端 `maxlength` 限制；接口必须自己校验。

**验收**

- 超长标签/分类/敏感词/平台字段/举报理由/改判原因 → 400，提示具体字段上限；
- 正常长度 → 200；
- 日志里不再出现 “Data too long for column”。

**预计**：0.5–1 天

## 六、P2：登录限流（可延后）

**现状**：登录失败无限尝试；安全审查把“登录失败锁定”列为本地演示可不做。

**如果要做**（不引入 Redis）：

- `ConcurrentHashMap<String, FailureWindow>`，key 用 `username + IP`；
- 5 次失败 / 5 分钟 → 锁定 5 分钟，返回 429/“尝试过多，请稍后再试”；
- 成功登录清零；定时清理过期 key；
- 不记录明文密码；日志只记 username/IP/次数。

**验收**：连续 5 次错误密码 → 第 6 次 429；等待窗口后恢复；正确密码不受影响。
**预计**：0.5 天；本地答辩可不做。
