# 阶段 6 开发笔记：跨平台内容适配

> 日期：2026-10-19　｜　入口：阶段 5（审核 Agent 已完成）　｜　详细设计见
> [适配规则与提示词设计说明](../设计文档/适配规则与提示词设计说明.md)

## 一、这一阶段做了什么

把「一篇稿件 → 多个平台版本」打通，形成完整链路：

```
前端选稿/选平台
  → 主系统组装平台约束 + 平台规则
  → Agent 逐平台改写（模型）
  → 程序格式自检（字数/标签）
  → 逐平台合规预检（复用审核 judge）
  → 结果落 audit_adaptation（版本递增）
  → 前端卡片展示、复制全文、回看历史
```

新增/修改的主要文件：

| 文件 | 作用 |
|---|---|
| `agent/api/adapt.py` | `/api/agent/adapt`：逐平台改写、格式自检、合规预检、回放 |
| `agent/format_check.py` | 确定性格式校验与标签规则解析 |
| `agent/judge.py` | 从 `api/audit.py` 抽出的判定核心，**审核与适配预检共用** |
| `agent/prompts.py` | 适配系统提示 + 平台形态要点 + 适配用户提示 |
| `backend/.../AdaptServiceImpl.java` | 组装上下文、落库、版本号、降级、数据权限 |
| `backend/.../AdaptController.java` | 两个适配接口 |
| `frontend/src/views/creator/adapt/index.vue` | 适配页（选稿、选平台、结果卡片、历史） |
| `db/04_phase6.sql` | 已有库的增量脚本（version 列、微博/B站约束、审核员菜单） |

## 二、关键取舍

### 1. 每个平台单独调用模型

合并成一次调用更省 token，但多平台输出容易过长被截断，一处 JSON 坏掉就全废。
分开调用还带来两个好处：一个平台失败不影响其他平台；提示词可以按平台写具体。
代价是耗时线性增长 —— 实测小红书 + 微博约 6.3 秒，三个平台约 9.3 秒。
因此把目标平台限制在 5 个，并把适配的读超时单独放宽：

- Agent 单次模型调用：25 秒（不变）
- 主系统适配客户端：120 秒（**审核仍是 30 秒，不能共用**）
- 前端 axios：180 秒（全局默认 30 秒会把正常的慢请求误判成网络异常）

### 2. 格式自检必须由程序算

字数、标签数量是可精确计算的。交给模型既浪费 token，又会让结果随模型状态波动。
程序算出来的结果才是阶段 8 "格式约束满足率"的可复现指标。
模型只负责创作，程序负责验收 —— 这个分工答辩时要讲清楚。

### 3. 合规预检复用审核的 `judge()`

抽出了 `agent/judge.py`，`/audit` 与 `/adapt` 都调用它。
如果各写一套，迟早会出现"适配页说通过、审核工作台说违规"的自相矛盾，
人机协同最忌讳系统自相矛盾。重构后跑了一次 `PRE_CHECK` 回归：违规等级、命中规则、片段定位都正常。

### 4. 标签只放 tags 字段

模型有很强的"平台习惯"：小红书/微博的内容天然带话题标签，它会顺手写进正文。
第一次生成时正文末尾有一行标签，UI 又单独展示 tags 并"复制全文"再拼一次 → **重复两遍**。

修复分两层：

1. 提示词改为"标签只放 tags 字段，不要写进正文"，平台要点里也去掉"末尾放标签"的说法；
2. 程序兜底：`_strip_duplicate_tags()` 只删除"整行全部是已有标签"的末尾行，
   有一个陌生标签就保留，避免误删正文。

改完后重新生成（v5），正文不再带标签，复制全文只出现一次。

### 5. 平台约束不是拍脑袋写的

种子数据原本是"常用参考值"，这一阶段逐个核对：

- **微博**：原写 140 字是错的。2016 年起原创微博上限 2000 字，140 只是信息流展示长度；
  改为上限 2000，风格要求"重点放在前 140 字"。
- **B站**：专栏（40 字标题 / 200-20000 正文）与视频投稿（80 字标题 / 2000 简介）是两套规格；
  本系统按视频投稿处理，`style_desc` 里写明。以后要做专栏应新增平台标识，不能混用。
- 公众号 64/20000、小红书 20/1000、抖音 55/1000 与核对结果一致。

页面顶部仍保留"数值以平台公开规范为准"的提示：平台会改版，数据在数据库里，改一行即可。

## 三、踩过的坑

| 问题 | 原因 | 修复 |
|---|---|---|
| Mock 适配的标题把正文也吃进去了 | `_search` 用了 `re.S`，`(.+)` 跨行匹配 | 标题改用 `([^\n]+)` |
| 前端 30 秒超时 | 全局 axios 默认 30s，5 平台可能更久 | 适配单请求设 180s |
| 审核员没有"跨平台适配"菜单 | 种子只给创作者发了 43 号菜单 | `04_phase6.sql` 补 `(2,43)`，种子同步 |
| "本平台不是适配目标"返回 500 | `BizException` 默认 500 | 输入校验改 400 |
| 第一次 UI 生成失败但没看到原因 | 重启 Agent 后没等健康检查就点了生成，请求被拒 | 重启后先轮询 `/health` 再操作；页面对 `agentFailed` 有明确提示 |
| Agent 重启后首次适配 0.1 秒失败 | 后端复用了已失效的 keep-alive 连接，而适配当时不重试 | 适配强制短连接（`Connection: close`）；只对"连接被拒绝"重试一次 —— 这种失败能确定请求没送达，重试安全 |
| 长文适配抖音输出 1242 字，超 1000 上限 | 模型对长文"舍不得删"，只给上限约束不住 | 提示词改为"目标为上限的 85%"，抖音明确 ≤800 字、只讲 3-5 个重点；复测 767 字通过 |
| 单元测试里 `check()` 勾不上 | Element Plus 的 checkbox 被 label 的 span 覆盖 | 测试改为点击可见标签文字（真实用户行为），不是代码 bug |

## 四、验证结果

### 端到端脚本 `tools/verify_stage6.py`

全部通过：

- 平台清单可读，5 个外部平台可用
- 参数校验：`local` 被拒、6 个平台被拒（400）
- 数据权限：creator2 适配 creator 的稿件 → 403
- 生成：小红书 + 微博，返回顺序与请求一致，格式自检字段完整，合规预检有风险等级
- 落库：首次 v1；再次生成 → v2；管理员可适配任意稿件
- 真实模型耗时：2 平台 6.3 秒；三个平台 9.3 秒
- 成本：2-3 个平台约 0.01 元/次（含两次模型调用/平台）

### 长文验证（2102 字，2026-10-19）

用户要求专门验证长文本，于是新建了一篇 2102 字、13 段的全屋收纳稿件
（稿件 id=16，留在库里作为长文演示样本），末尾埋了"加我微信发你"作探针。

| 平台 | 首次结果 | 修复后 | 格式 | 合规 |
|---|---|---|---|---|
| 小红书 | 937 字 | **874 字** | 通过 | 通过 |
| 微信公众号 | 2203 字 | **2161 字** | 通过 | 通过 |
| 抖音 | **1242 字（超限）** | **767 字** | 通过 | 通过 |

- 小红书把 2102 字压到 874 字，核心步骤保留、次要细节删减，说明压缩路径可行；
- 抖音首轮超限 24%，修复提示词后降到 767 字（目标 800 以内）；
- 三个平台的版本都删除了"加我微信"，合规预检均通过；
- 三平台一次 18.5 秒，`promptTokens=13000 / completionTokens=3593`，成本约 0.027 元；
- 还顺带发现并修复了"Agent 重启后复用失效连接"导致的偶发降级。

**结论**：长文适配可用，但必须给"目标长度"而不只是"上限"；抖音这类强形态约束的平台要在
`PLATFORM_HINTS` 里单独给预算。

### 界面验证（浏览器实际操作）

- 创作者登录 → 创作中心 → 跨平台适配
- 选稿件 #1 → 勾选小红书 + 微博 → 生成
- 结果卡片：格式通过、合规通过、标题/正文字数、标签、复制全文
- 适配历史：v1…v5 按时间倒序，可查看详情
- 源稿件预览、平台约束提示均正常显示

## 五、已知局限（答辩要主动说）

1. **不做真实发布**，只到"可复制成品 + 预检"。这是由平台接口现实决定的（D-M1）。
2. **不校验事实真伪**：只能约束不新增原文没有的信息。
3. **串行生成**：短文本 3 平台约 9 秒，2100 字长文 3 平台约 18.5 秒，5 平台长文约 30-40 秒；
   可改并行，但日志和错误定位会更复杂。
4. **标签规则是自由文本**：靠"N-M 个 / 不使用"的约定解析，管理员写模糊描述时只校验存在性。
5. **适配质量未量化**：格式满足率已有，风格/信息保留度要等阶段 8 的人工评分。
