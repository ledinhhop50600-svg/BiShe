## 二、几个关键设计（答辩要讲）

### 1. 规则由主系统下发，Agent 无状态

Agent 不连 MySQL、不持有业务数据；每次请求由主系统把"稿件内容 + 平台约束 + 本次可用规则"一起传过去。
好处：
- 主系统是规则与平台配置的**唯一数据源**，不会出现两边数据不一致；
- Agent 可以独立启动、独立测试、随时替换实现（换模型、换框架、甚至换语言），不牵动主系统；
- 降级简单：Agent 整个不可用，主系统只是少了一个能力。

### 2. 超时层级：Agent 必须比主系统先超时

```
主系统读取超时 30s  >  Agent 内部模型超时 25s  >  模型服务实际耗时
```
如果反过来（Agent 比主系统慢），主系统会先断开，拿不到任何错误信息，日志里只能看到一个"读取超时"。
让 Agent 先超时，它能返回「模型调用超时」这样具体的原因。

### 3. 降级不是"吞掉错误"，而是"如实上报"

智能体不可用时，接口仍返回 200，但结果是：
```json
{ "agentFailed": true, "error": "...", "message": "智能体服务不可用，请改为人工审核" }
```
这样界面可以明确提示"这次没有智能体结论，请人工审核"，而不是让审核员对着空白猜。
实测：停掉 8001 后调用，返回 `agentFailed=true`，业务不中断。

### 4. 回放模式的两面性

它是测试设施，不是业务能力：同一 requestId 返回缓存结果。用途是**重复评测不花钱、断网可回归、演示可兜底**。
但它也带来一个陷阱：**改了提示词之后如果还用旧 requestId，会拿到旧结论**。所以跑评测时必须每次生成新 requestId。

## 三、Mock 供应商为什么要单独存在

没有 API Key 时，整条链路（主系统组装上下文 → HTTP → 结构化结论 → 前端展示）本该完全无法验证。
Mock 供应商解决这个问题：它按关键词给出**确定性**结论，让链路可以真正跑通、让测试可以稳定回归。

它在实现上有一个细节值得记：**只能检查"待审核内容"那一段**。
提示词里包含规则文本，而规则文本本身就写着"国家级""全网最低价"这些词 —— 如果在整段提示词里做关键词匹配，**规则会命中自己**，产生假阳性。
所以 `prompts.py` 用【待审核内容】【输出要求】两个标记把文章段落框起来，Mock 只在框内匹配。这个坑在写的时候想到、并用实测确认了（违规稿件命中 4 条、正常稿件 0 条）。

## 四、你必须能讲出来的 3 件事

1. **主系统和智能体是什么关系**：主系统管数据与流程，智能体只做判定；两者通过两个 HTTP 接口解耦，规则由主系统下发、Agent 无状态。Agent 挂了，主系统退回人工审核，业务不停。
2. **为什么要有 Provider 抽象和 Mock 模式**：换模型只改配置；没有 Key 或断网时，仍能用 Mock 跑通链路与回归测试 —— 测试不依赖外部服务的"心情"。
3. **降级是怎么做的**：超时分层（Agent 先超时）+ 失败重试一次 + 返回带 `agentFailed` 标记的结果，界面据此提示人工审核。
