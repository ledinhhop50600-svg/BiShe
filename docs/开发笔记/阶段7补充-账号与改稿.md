## 二、D1 注册与个人中心

### 实现

| 能力 | 做法 |
|---|---|
| 验证码 | 算式（1-9 相加），答案只存服务端；一次性使用；5 分钟过期；`SecureRandom`；内存 Map（无 Redis，D-P5） |
| 注册 | 账号 3-20 位字母/数字/下划线；密码 ≥6 位且同时含字母与数字；两次一致；验证码 |
| 角色 | 查询 `role_key=creator` 后关联，**不接受前端传角色** |
| 注册后 | 直接签发令牌登录，省一次输入 |
| 个人资料 | 昵称/邮箱/手机号可改；账号名不可改 |
| 改密码 | 验证原密码；新旧不能相同；两次一致；成功后 `StpUtil.logout()` |
| 找回密码 | 不做（无短信/邮件渠道）；管理员可在用户管理里重置 |

接口：`GET /api/auth/captcha`、`POST /api/auth/register`、`GET/PUT /api/profile`、
`PUT /api/profile/password`。前两个加入 Sa-Token 白名单。

### 关键取舍

1. **验证码放内存而不是 Redis**：本项目只在本机跑，不引入 Redis；进程重启后验证码失效是正常行为。
   同时设置 5 分钟过期与一次性使用，挡住最简单的脚本重放。
2. **注册固定创作者角色**：这是安全边界，不是产品偏好。如果注册时能选角色，
   任何人都能注册成审核员并放行自己的内容。
3. **账号名不可改**：它是登录凭据，也是 `audit_record` / `audit_review` / 稿件作者字段里的身份标识。
   允许改名会破坏历史可追溯性；主流平台同样不允许。
4. **改密后让令牌立即失效**：即使会话被别人占用，改密后对方也会被踢下线。
   前端用 `logoutLocal()` 只清本地状态，不再调 `/auth/logout`（令牌已失效，再调会报 401 并弹错误提示）。

### 踩到的细节

- **清空邮箱/手机号**：MyBatis-Plus 默认忽略 null 字段，`updateById` 传 null 不会把列清空。
  改为传空字符串（`trimToEmpty`），才能真的清掉。
- **注册校验顺序**：验证码先校验（一次性），再校验两次密码。验证码失败后必须换一题，
  前端在注册失败时自动 `refreshCaptcha()`。
- **`@Email` 与空值**：Jakarta 的 `@Email` 允许 null/空串，正好符合"邮箱选填"。

## 三、D3 已发布稿件编辑后重审

### 行为（方案 B）

- 已发布（2）/已下架（5）的稿件允许编辑；
- **保存即回到待审核（1）**，内容广场立刻不再展示；审核通过后重新发布；
- 编辑时风险等级重置为 -1、驳回原因清空；
- 审核工作台会用 `content_hash` 发现旧初审结论已过期，要求重新初审。

### 为什么必须"保存即待审"

如果只保存内容、不改状态，线上内容就绕过审核被改掉了 —— 这正是方案 A（直接改）的问题。
所以状态变更放在**后端 update** 里，前端无法绕过；前端只负责提示影响。

### 前端

- 「我的稿件」：状态 2/5 显示「编辑并重审」，点击先弹出警告（审核期间不对外展示）；
- 投稿页：这两种状态只显示「发布前检查」+「保存并提交审核」，不再显示"保存草稿"，
  避免用户以为只是存了草稿。

## 四、验证结果

`tools/verify_account_revision.py` 全部通过：

- **验证码**：错误答案 400；同一验证码复用 400（一次性）；
- **注册**：正确验证码 200，直接登录，角色 `creator`；重复账号 400；两次密码不一致 400；
- **个人资料**：读取/修改成功；非法邮箱 400；
- **改密**：原密码错误 400；正确改密 200；旧令牌访问 401；新密码可登录、旧密码不可；
- **D3**：创建并发布（状态 2）→ 广场可见 1 条 → 编辑 → 状态 1、风险 -1 → 广场可见 0 →
  重新审核通过 → 状态 2 → 管理员下架（5）→ 编辑 → 状态 1；
- **权限**：未登录访问个人中心 401。

浏览器实际走查：登录页「立即注册」→ 验证码弹窗 → 注册并自动登录 → 顶部「个人中心」→
修改昵称/邮箱（页头昵称同步更新）→ 创作者「我的稿件」看到「编辑并重审」→
确认弹窗 → 投稿页显示"保存后进入待审核"且只有「保存并提交审核」。
