# 阶段 7 开发笔记：人机协同闭环

## 一、这一阶段做了什么

把「投稿 → 初审 → 终审 → 反馈 → 重提」整条链路走通，并让每次判定与改判都可追溯：

| 能力 | 落点 |
|---|---|
| 智能体初审留痕 | `audit_record`，每次一条；失败也留（`agent-failed`） |
| 审核员采纳/改判 | `audit_review`（1 采纳 / 2 改判 / 3 人工判定），改判原因必填 |
| 工作台 Agent 面板 | 等级、理由、命中规则、违规片段、建议、token/耗时 |
| 创作者反馈 | 违规片段高亮 + 逐条修改建议 + 审核员意见 |
| 审核记录页 | 可筛选、可看详情，论文原始数据入口 |
| 看板统计 | 判定分布、采纳/改判/人工判定、改判率、失败数 |
| 结论过期保护 | `content_hash` 绑定"这一版内容" |

新增/修改的主要文件：

| 文件 | 作用 |
|---|---|
| `entity/AuditRecord.java`、`AuditReview.java` + Mapper | 两张表的映射 |
| `service/AuditRecordService(+Impl)` | 留痕、反馈查询、分页、统计 |
| `service/AuditAgentService` | POST_AUDIT 落库；PRE_CHECK 不落库 |
| `service/impl/ArticleServiceImpl.review` | 采纳/改判判定、`audit_review` 落库、改判原因校验 |
| `common/ContentHash.java` | 标题+正文 SHA-256 |
| `controller/AuditRecordController` | 记录页与统计接口 |
| `views/audit/workbench` | Agent 面板 + 采纳/改判交互 |
| `views/audit/record` | 审核记录页 |
| `views/creator/article`（反馈弹窗） | 创作者看到的片段与建议 |
| `views/dashboard` | 人机协同统计 |
| `db/05_phase7.sql` | 已有库的 `content_hash` 增量脚本 |

## 二、关键取舍

### 1. 初审由审核员显式触发，不在投稿时自动跑

投稿接口不能被模型拖慢（审核客户端 30 秒、失败还重试一次），而且自动跑完再等人打开，
结论可能已经过期。显式按钮把可控性放在第一位；没有消息队列时不引入异步任务（D-P5）。

### 2. 采纳/改判的口径

- AI 说通过/疑似，人驳回/阻断 → 改判；
- AI 说违规/严重，人通过 → 改判；
- **AI 说疑似，人通过或驳回都不算改判** —— 疑似是"转人工"信号，不是结论。

改判率 = 改判 /（采纳 + 改判）。人工判定（未跑/失败/内容已改）不进分母，
否则"智能体没跑"会被算成"人和 AI 不一致"。

### 3. 结论过期用内容哈希，不用更新时间

最初的实现用 `create_time < update_time` 判断。验证脚本发现：**稿件修改与初审落在同一秒时，
DATETIME 只到秒，比较结果永远是"未过期"**，旧结论会被误用。

改为 `content_hash`（标题+正文 SHA-256）：初审时存，读取反馈与审核时重算比对。
改过即过期，与时间精度无关；改回原内容时哈希相同，结论仍然有效，也符合直觉。

### 4. `audit_review.audit_record_id` 是 NOT NULL，怎么办

审核员可能没跑初审就直接审。为了不丢审核数据，后端补一条 `model_name=no-agent`
（或 `content-changed`）的 `audit_record`，再让 `audit_review` 引用它。
这样每次人工处理都能追溯到一条"判定依据"，记录页也不会出现空指向。

### 5. 预检不落库

创作者点"发布前检查"可能点很多次，每次都落库会污染工作台与统计。
只有 `POST_AUDIT`（正式审核）留痕；预检结论只作为提示。

## 三、踩过的坑

| 问题 | 原因 | 修复 |
|---|---|---|
| 重提后旧结论仍被当成有效 | `DATETIME` 只到秒，同秒修改比较失效 | 改用内容哈希 `content_hash` |
| 审核记录页需要文章标题/审核员名 | 逐条查会 N+1 | 批量取稿件、审核意见、用户 |
| 创作者反馈看不到 AI 片段 | 原弹窗只显示 `rejectReason` | 增加 `/audit-feedback`，弹窗展示结构化片段与建议 |
| 审核接口返回 void，前端不知道记录是否落成功 | 只能靠刷新 | 工作台操作后重新拉反馈；后端事务保证三张表一致 |
| 工作台调用初审 30 秒超时 | 全局 axios 30 秒，后端审核还要重试 | 单请求放宽到 90 秒 |

## 四、验证结果

### 端到端脚本 `tools/verify_stage7.py`（全部通过）

- 违规稿件初审 → 违规（2），4 处违规片段；
- 审核员驳回 → `audit_review` 记为**采纳**；
- 创作者修改重提 → 旧记录 `stale=true`，旧审核意见被隐藏；
- 重新初审 → 通过（0）；审核员驳回 → **改判**（原因必填，无原因被拒）；
- 审核记录页能看到记录与改判；统计：4 条记录、采纳 2、改判 2、改判率 50%；
- 权限：创作者看记录页 403；他人看反馈 403。

### 浏览器实际走查

- 审核员登录 → 工作台 → 选稿 → 运行初审（2.8 秒）→ 面板显示违规/规则/4 处片段/建议；
  默认动作自动切到"驳回"，关系显示"采纳智能体建议"；填原因提交 → 队列 5→4；
- 审核记录页：记录、token、耗时、人工处理（采纳/改判）、意见都正常；
- 创作者登录 → 我的稿件 → 查看反馈：审核意见 + 智能体初审 + 4 处片段与修改建议 + "采纳（最终：违规）"；
- 看板：智能体审核 4 次、改判率 50%、判定分布与人工处理分布正常。

## 五、已知局限

1. 只有一个审核员账号，改判率是单人数据；多人一致性留到后续。
2. 没有"同一稿件版本对比"界面，但数据（每次记录 + 内容哈希）已经齐了。
3. 没有审核时效统计；字段够，属于看板增强。
4. 改判原因是自由文本，尚未做原因分类（阶段 8 可人工归因）。
5. 初审是按钮触发，不是提交即审；无消息队列下的取舍。
