## 二、踩到的坑（这节是本笔记最有价值的部分）

### 坑 1：start.spring.io 生成的版本号在 Maven 仓库里不存在

- **现象**：`mvn compile` 报 `Non-resolvable parent POM ... spring-boot-starter-parent:pom:4.1.1.RELEASE (absent)`。
- **原因**：start.spring.io 的版本标识是 `4.1.1.RELEASE`，但 Maven 中央仓库中的真实坐标是 **`4.1.1`**（没有 `.RELEASE` 后缀）。直接查仓库元数据确认：`4.1.1.RELEASE` 返回 404，`4.1.1` 返回 200。
- **解决**：把 `pom.xml` 里的 `4.1.1.RELEASE` 改成 `4.1.1`。
- **经验**：**不要相信脚手架生成的版本号，以仓库里实际存在的坐标为准**。查证方法：直接请求仓库的 `maven-metadata.xml`。

### 坑 2：Spring Boot 4 的 starter 名字变了

- **现象**：官方脚手架生成的是 `spring-boot-starter-webmvc`（不是 Boot 3 时代的 `spring-boot-starter-web`），测试依赖也被拆成了 `spring-boot-starter-webmvc-test`、`spring-boot-starter-validation-test`。
- **原因**：Boot 4 做了 starter 模块化重构。
- **影响**：网上的 Boot 3 教程里的依赖名照抄会失败；写文档和答辩时要注意别写成旧名字。
- **另一个相关发现**：Spring 官方的 `mybatis-spring-boot-starter` 目前只声明支持到 `4.1.0.M1`（即不支持 4.1.x）。**我们用 MyBatis-Plus 自己的 `mybatis-plus-spring-boot4-starter`，因此不受影响**——这也顺便说明了当初选 MyBatis-Plus 而不是原生 MyBatis 的好处。

### 坑 3：MySQL 命令行导入中文 SQL 变乱码

- **现象**：脚本执行成功，但数据库里的中文变成 `閾捐矾宸叉墦閫氾細...`，接口返回也是乱码。
- **原因**：Windows 上的 mysql 客户端默认字符集不是 utf8mb4（按系统区域走 GBK），导入 UTF-8 编码的 `.sql` 文件时，客户端把 UTF-8 字节按 GBK 解释，再存进库里就成了乱码。**库和表本身是 utf8mb4，问题出在客户端这一侧。**
- **解决**：导入/查询时显式指定字符集：

  ```bash
  mysql -u zimeiti -p zimeiti --default-character-set=utf8mb4 < db/xx.sql
  ```

- **经验**：**阶段 1 导入建表脚本时同样要加这个参数**，否则表注释和种子数据会全部乱码。另外，验证中文是否正确不能靠在终端里肉眼看——终端编码会变，容易误判。本项目用 `tools/verify_chain.py`（把中文转成 Unicode 码点输出）来验证，不受终端影响。

### 坑 4（工具类）：Git Bash 里用 robocopy 参数会被误转

- **现象**：`robocopy 源 目标 /E` 报错 16（严重错误，零文件复制）。
- **原因**：Git Bash（MSYS2）会把以 `/` 开头的参数当路径转换，`/E` 被转成 Windows 路径。
- **解决**：命令前加 `MSYS_NO_PATHCONV=1`。

### 坑 5：批处理脚本的中文与换行符（本阶段踩得最久的一个）

- **现象**：双击 `start.bat` 后满屏报错 —— `'cho' 不是内部或外部命令`、`'73' 不是内部或外部命令`、`'ttp:' 不是内部或外部命令`，两个服务一个都没起来。
- **原因（两个问题叠加）**：
  1. **换行符**：编辑器/工具默认生成的是 **LF** 换行，而 cmd.exe 解析批处理文件要求 **CRLF**。用 LF 会让它把行切断，把中文片段当成命令去执行（这就是 `'cho'` 这种"少一个字母"的报错来源）。
  2. **编码**：批处理里的中文必须用系统 OEM 编码（中文 Windows 是 **GBK / CP936**）。常见的"用 UTF-8 保存 + 在文件开头写 `chcp 65001`"是个经典陷阱 —— cmd.exe 按**字节偏移**记录解析位置，中途切换编码会导致后续行全部错位。
- **解决**：文件保存为 **GBK + CRLF**，并且**不要在批处理里写 chcp**。
- **验证方法（重要）**：把脚本用 `cmd /c "chcp 936 >nul & 脚本.bat"` 运行（模拟双击时的中文控制台环境），输出重定向到文件后**按 GBK 解码**检查。**不要直接在 Git Bash 窗口里肉眼看中文输出** —— 该窗口的编码会变，看着像乱码不代表文件有问题（本阶段为此误判过两次）。

### 坑 6：MySQL 运行状态的检测方式

- **现象**：MySQL 明明在运行，脚本却判断为"未运行"，进而执行 `net start MySQL80` 并报"发生系统错误 5（拒绝访问）"。
- **原因**：原写法 `sc query MySQL80 | find "RUNNING"` 在这台机器上没能匹配到（`sc` 的输出与匹配词不完全一致）。
- **解决**：改为直接检测 **3306 端口是否在监听**：`netstat -ano | findstr ":3306" | findstr "LISTENING"`。这比匹配服务状态文本更直接，也更贴近我们真正关心的问题（应用能不能连上数据库）。
- **顺带说明**：`net start` 需要管理员权限，所以脚本里对启动失败的提示写了"右键以管理员身份运行"这条路径。

### 坑 7：8000 端口上跑着别人的服务

- **现象**：智能体服务启动日志报 `[Errno 10048] error while attempting to bind on address ('127.0.0.1', 8000)`；但访问 `http://localhost:8000/health` 返回 404，而 `/docs` 却返回 200 —— 看起来"服务起来了但接口不对"。
- **原因**：8000 端口上实际运行着**另一个项目**（`设备故障诊断 Agent`，提供 `/api/inspect` 等接口）。本项目启动失败，访问到的其实是别人的服务 —— 所以 `/docs` 有响应但 `/health` 不存在。
- **解决**：本项目智能体服务固定使用 **8001** 端口（`agent/main.py` 与 `start.bat` 已统一）。
- **经验**：服务起不来时，先确认**端口上到底是谁**：`netstat -ano` 拿 PID，再看 `/openapi.json` 里的应用名。否则很容易对着别人的服务调半天接口。

## 三、关键概念解释（答辩要用）

- **前端为什么要有 Vite 代理？** 浏览器有同源策略：页面在 5173 端口，后端在 8080 端口，直接请求属于跨域会被浏览器拦截。所以在 `vite.config.js` 里把 `/api` 开头的请求转发给 8080，浏览器看起来始终在跟 5173 说话。
- **为什么数据库不用 root 账号？** 最小权限原则：应用只需要一个库的读写权限。`db/00_create_database.sql` 创建的 `zimeiti` 账号只对 `zimeiti` 库授权。
- **MyBatis-Plus 帮我做了什么？** `DemoPingMapper` 里一行方法都没写，但 `selectList(null)` 就能查出全部数据——SQL 是框架根据实体类上的 `@TableName` 和字段自动生成的。这就是"单表 CRUD 免写 SQL"。

## 四、你必须能讲出来的 3 件事

1. **一次请求经过了哪几层**：浏览器页面（Vue）→ Axios 发请求 → Vite 代理转发到 8080 → Spring Boot 的 `PingController` → `DemoPingMapper` → MySQL 查询 → 结果按 JSON 原路返回并渲染成表格。
2. **你的项目由几个部分组成、各自的端口和职责**：前端 5173（界面）、后端 8080（接口与业务）、MySQL 3306（数据）、智能体服务 8001（后续的审核与跨平台适配）。
3. **`start.bat` 做了哪几件事**：检查 MySQL 服务 → 分别启动后端、前端、智能体三个服务 → 等 25 秒 → 逐个检查端口是否就绪 → 自动打开页面。
