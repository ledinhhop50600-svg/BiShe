# 创新点与 Agent 设计决策（主题：agent）

> 记录本系统创新点（单智能体）的形态、边界与演进方向。

## D-A1 创新点主线：智能审核 Agent（方向 A）

- **结论**：系统创新点定为「智能审核 Agent」—— 自媒体平台稿件自动审核：违规规则库 RAG 检索 → 风险分级判定（含理由）→ 处置建议 → 人工复核/申诉闭环。
- **理由**（四条，按答辩/求职两个场景的权重排序）：
  1. **业务动机天然成立**：内容审核是自媒体平台的法定义务（平台主体责任），不是硬塞进系统的功能。答辩时「为什么要有这个 Agent」一句话能答完，这是最容易被追问、也最容易守住的一环。
  2. **能产出论文需要的量化实验**：审核结果有客观对错，可构造评测集计算准确率/召回率/F1，并做「纯关键词规则 vs 纯 LLM vs RAG+LLM」对比实验，直接支撑论文的实验章节。普通「大模型写文案」类毕设拿不出这类数据。
  3. **技能点命中 Agent 岗位核心**：RAG 规则检索、工具调用、多级处理决策、人工兜底与反馈闭环、效果评测 —— 这几项在 Agent 应用开发 JD 中反复出现。
  4. **演示稳定直观**：投递违规稿件 → 分级判定 + 理由 → 人工复核放行。不依赖生成质量的随机性，演示不会翻车。
- **已排除的备选**：
  - B 运营问数 Agent（Text2SQL/ChatBI）：企业落地主流、工程含金量高，但数据要自养，与「自媒体平台」业务咬合偏弱。
  - C 内容生产 Agent：同类毕设数量多，答辩容易被认为「套壳调用」；生成质量难量化评估。
  - D 综合助手（一开始就挂多类工具）：易陷入「什么都会 = 什么都不精」，代码量与答辩风险均最大。
- **日期**：2026-10-16

## D-A2 目标架构：单 Agent + 工具注册表

- **结论**：实现为**一个** Agent，各项能力通过工具注册表挂载（规则库检索、稿件/历史数据查询、处置执行、评测工具等）。题目中的「单智能体」由此落地。
- **理由**：贴合毕设题目；单 Agent 的调试与演示成本远低于多 Agent 编排；工具注册表本身即天然的扩展边界。

## D-A3 为多 Agent 与内容生产（C）预留扩展口，但当下不预建

- **结论**：架构上把三层抽象切开 —— ①Agent 主循环（规划/工具选择/终止条件）②工具接口（统一 schema + 注册机制）③上下文与记忆管理。当前**只实现单 Agent，不引入多 Agent 编排**。后续若加 C（内容生产）：先作为**工具**挂到同一 Agent；只有当它确实需要独立上下文与长流程时，才升级为独立 Agent。
- **理由**：用户明确保留「后续加 C」与「转多 Agent」的可能。为未来的可能性预先引入编排框架，是让现在多付复杂度而收益为零；但把上述三层抽象切干净，未来升级是「加一层」而非「重写」。判断标准写在结论里，避免到时候拍脑袋。
- **待定**：C 的挂载方式（工具 or 独立 Agent）留到真正实施 C 时，按上面的判断标准决定。
- **日期**：2026-10-16

## D-A4 实施顺序：管理系统主体优先，Agent 后置 —— 但数据模型必须预埋

- **结论**：按用户意愿排序 —— 先完成用户管理、角色权限、菜单，再做内容管理与 Agent。同时设三条硬约束：
  1. **数据库设计从第一天就包含 Agent 所需的表**：稿件、审核任务、审核结论、规则库、处置记录、申诉记录。
  2. **「内容 / 稿件管理」属于第一批必做模块** —— 它是 Agent 的输入对象；没有它，Agent 无真实数据可审。
  3. **Agent 的对外契约在内容模块阶段就定死**：提交审核 → 返回「风险分级 + 判定理由 + 处置建议」。之后无论 Agent 用 Java 还是 Python 实现，契约不变。
- **理由**：用户希望先做"学校要求的主体"再加"自己想做的创新点"，顺序本身合理（权限系统也确实应先于 Agent，因为复核与申诉都依赖权限）。但"主体做完再追加创新点"的典型失败模式是：Agent 阶段开始时无真实数据可用，只能造假数据演示，创新点变成挂在角落里的空壳。这三条约束以最低成本消除该失败模式。
- **日期**：2026-10-16

## D-A5 模型供给：DeepSeek 为主 + 免费额度兜底，必须做 Provider 抽象

- **结论**：主用 DeepSeek；预算紧张时降级到免费额度（硅基流动 / 智谱）。代码中必须存在模型 Provider 抽象层（走 OpenAI 兼容接口），支持一键切换模型与自动降级。
- **理由**：月预算 ≤ 50 元；开发期反复调 prompt 会持续消耗 token，需要便宜模型 + 免费额度兜底。Provider 抽象同时服务于论文里「不同模型效果对比」的实验。
- **日期**：2026-10-16

## D-A6 Agent 实现语言：独立 Python 服务（已定）

- **结论**：Agent 实现为**独立 Python 服务**（FastAPI 暴露 HTTP 接口），SpringBoot 后端通过 HTTP 调用；模型调用走 OpenAI 兼容接口（DeepSeek 为主，见 D-A5）。
- **理由**：① 用户未学过 Java、对 Python 较熟（学过 FastAPI），而目标岗位 Agent 应用开发的主流生态在 Python —— 放在 Python 里既顺应用户既有基础，也是求职能讲的部分；② D-A4 已把对外契约定死，语言选择不影响主系统，事后改动范围可控；③ 「Java 主系统 + Python 智能体服务」是真实企业里常见形态，答辩与面试都有话讲。
- **待定**：Agent 内部是否引入现成框架 —— 倾向**自研轻量主循环**（规划 / 工具选择 / 终止条件）+ 成熟库仅用于向量检索与评测，理由是这样答辩能讲透、面试可深入。待技术调研后定案。
- **日期**：2026-10-16

## D-A7 人机协同：两阶段介入 + 审核员终审

- **结论**：
  1. **两阶段介入**：①投稿前预检 —— 创作者点击提交前，Agent 先做风险预判，给出风险提示与修改建议（不阻断）；②发布后审核 —— 创作者提交发布申请后，Agent 做分级初判 → 审核员复核/改判 → 终审。
  2. **Agent 只输出「分级建议 + 判定理由 + 处置建议」，不单独决定通过或阻断**；审核员可复核、改判并修改最终结果。
  3. 判为违规时，必须向创作者反馈**具体违规内容片段 + 修改建议**；创作者可修改后重新提交。
- **理由**：用户明确要求（兼顾平台审核责任与创作者体验）。两阶段还让 Agent 在系统里有两个真实触点，演示路径更丰富。
- **额外收益**：**审核员的改判记录即人工标注数据**，可回流为评测集样本与规则库优化依据 —— 这比纯合成样本可信，缓解「评测集从哪来」的问题。
- **日期**：2026-10-16

## D-A8 功能范围与角色（定案）

- **角色（3 种）**：超级管理员 / 审核员 / 创作者
- **第一批模块**：用户管理、角色权限（RBAC）、菜单管理、**内容/稿件管理**、数据看板
- **第二批模块（创新点）**：内容审核智能体、人工复核工作台、规则库管理、审核效果评测
- **加做**：创作者投稿页（极简前台）、举报处理、敏感词库维护（对比基线）
- **砍掉**：评论管理、创作者收益分成、消息通知
- **理由**：范围收敛到「答辩能完整演示 + 论文有话可写」的最小集合。举报处理为 Agent 增加一条触发路径；敏感词库为论文提供必需的传统方案 baseline。
- **日期**：2026-10-16

## D-A9 评测集策略：公开数据集优先

- **结论**：优先检索并采用**公开的中文违规 / 内容安全数据集**（用户要求真实可靠）；合成样本仅作补充，用于覆盖规则库特有的、公开数据集缺失的违规类型（如广告法极限词）；规则库只用于 baseline 与样本生成辅助，**不得作为最终标注**，避免「用规则库标注的数据去测结合规则库的模型」这类循环论证 —— 该风险要在论文中主动说明。
- **附加数据来源**：审核员改判记录（D-A7）作为真实标注回流。
- **待办**：检索公开数据集并核验可得性（进行中）
- **日期**：2026-10-16

## D-A10 智能体能力扩展：跨平台内容适配 + 按平台规则预检（第二创新点）

- **结论**：Agent 能力从「单一内容审核」扩展为三项：
  1. **平台审核**（原有）：按本平台规则做分级判定，结果供审核员决策（人机协同，见 D-A7）；
  2. **按目标平台规则的合规预检**（升级）：创作者选定目标平台集合后，按各平台的规则集分别检查并给出修改建议；
  3. **跨平台内容适配**（**新增，第二创新点**）：同一份内容 → 生成各平台适配版本（小红书短文案 + 话题标签 / 微博 140 字 + 话题 / 公众号长文 / B站标题简介标签 / 抖音口播脚本），并附**格式约束自检**（字数、标签、结构等可自动校验）。
- **理由**：
  1. 用户认可该方向 —— 在没有真实平台对接的前提下，跨平台内容适配更具实际应用价值；
  2. 适配与规则预检**不依赖任何平台接口**，零风控风险，演示稳定；
  3. 对求职价值更高：多任务调度、结构化输出、风格控制、提示词工程，都是 Agent 应用开发岗位的核心能力项；
  4. 与 D-M1 的决策配套：系统保留「目标平台」概念但不做真实发布，价值由适配与合规承接。
- **设计要点**：**一个规则引擎，两处调用** —— 平台审核（运营方视角，决定本平台能否发布）与目标平台预检（创作者视角，适配前检查）共用同一套规则库；规则库按平台维度组织（通用规则 + 平台专属规则，见 D-M2）。
- **对阶段划分的影响**：新增独立阶段「跨平台内容适配」；评测阶段增加适配效果评估（格式约束满足率自动校验 + 人工评分 + LLM 评判与人工评分一致性）。
- **日期**：2026-10-16
