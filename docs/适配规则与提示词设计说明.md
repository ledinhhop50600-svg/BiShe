# 跨平台适配：规则与提示词设计说明

> 阶段 6 交付物。对应代码：`agent/api/adapt.py`、`agent/format_check.py`、`agent/prompts.py`、
> `backend/.../AdaptServiceImpl.java`、`frontend/src/views/creator/adapt/index.vue`。
> 契约：`docs/Agent接口契约-v1.md` 第三节（v1.1）。

## 一、目标与边界

**做什么**：把本平台的一篇稿件，改写成适合公众号 / 小红书 / 微博 / B站 / 抖音发布的版本；
每个版本都做**程序侧格式自检**与**按目标平台规则的合规预检**；结果可复制、可回看历史版本。

**不做什么**（答辩要主动说清）：

- **不做真实发布**。个人开发者拿不到各平台的发布接口（详见 `docs/decisions-multiplatform.md`），
  本功能止步于"生成可粘贴的成品 + 预检"。
- 只做**文本**。图片尺寸、视频封面、@ 与位置等内容不在本期范围。
- 不抓取平台实时规则。平台字数限制会改版，本系统按核对日期固化在数据库里，管理员可改。

## 二、平台格式约束（2026-10-19 核对）

数据落在 `audit_platform` 表，管理员可在「平台管理」页面修改。

| 平台 | 标题上限 | 正文上限 | 标签规则 | 形态要点 |
|---|---|---|---|---|
| 微信公众号 | 64 字 | 20000 字 | 不使用话题标签 | 正式长文，可保留段落与小标题 |
| 小红书 | 20 字 | 1000 字 | `#` 开头，3-5 个 | 口语化、少量 emoji、开头钩子 |
| 微博 | 无独立标题 | 2000 字 | `#话题#`，1-2 个 | 信息流只展示前 140 字，重点前置 |
| B站（视频投稿） | 80 字 | 2000 字（简介） | 3-5 个标签 | 标题说清主题，简介列看点 |
| 抖音 | 55 字 | 1000 字（描述） | 3-5 个话题 | 口播脚本，前 3 秒钩子 |

**核对说明（必须如实写进论文/答辩）**：

1. **微博不是 140 字上限**。2016 年起原创微博上限放宽到 2000 字（新华网、人民网 2016-11 报道）；
   140 字是**信息流展示长度**，超过后显示"全文"。所以系统把正文上限设为 2000，
   同时在风格要求里写明"重点放在前 140 字"。
2. **B站有两套规格**：专栏（标题 40 / 正文 200-20000）与视频投稿（标题 80 / 简介 2000）。
   本系统按**视频投稿**处理，因为 `style_desc` 要求"简介说明内容看点"。若以后做专栏，
   应新增一个平台标识（如 `bilibili_column`），不要在一个平台里混两套规则。
3. **小红书** 20/1000 是标准笔记的限制；2025 年内测的长文功能正文更长。本系统按标准笔记处理。
4. 数值来自官方接口文档、平台创作中心与主流报道的交叉核对；官方页面多需登录，
   **答辩前建议在 App 发布页再确认一次**。平台改版后只需改 `audit_platform`，不用改代码。

**字数怎么算**：程序按 Unicode 码点计数（`len()`），中文 1 字、emoji 1-2 个码点。
小红书的计数规则里"两个阿拉伯数字算一个字"、部分 emoji 算两个字，与我们的算法略有差异。
因此**生成时按上限的 90% 左右控制**，不要贴着上限写；格式自检是"保守估计"，不是平台最终判定。

## 三、处理流程

```
选稿（自己的稿件）
   │
   ├─ 主系统组装上下文：
   │    稿件标题/正文 + 目标平台约束 + 规则（通用规则 + 各平台专属规则，带 platformKey）
   │
   ▼
Agent /api/agent/adapt
   │
   ├─ 对每个目标平台（顺序与请求一致）：
   │    1. 改写：LLM 按平台形态生成 {title, content, tags}
   │    2. 清理：删掉正文末尾重复的标签行（只在整行都是已有标签时删）
   │    3. 格式自检：程序算字数、标签数量与格式（确定性）
   │    4. 合规预检：把 title+content+标签 交给 judge()，用该平台规则判定
   │
   ▼
主系统落库：audit_adaptation（每个平台一行，version 递增）
   │
   ▼
前端：分平台卡片 + 格式问题 + 合规结论 + 复制全文 + 历史版本
```

**为什么每个平台单独调用一次模型**：

- 合并输出容易变长，被 `max_tokens` 截断后整段 JSON 报废（阶段 5 踩过空输出的坑）；
- 一个平台失败不影响其他平台，提示词也能针对平台写得更具体；
- 代价是耗时随平台数线性增长，所以**一次最多 5 个平台**，前端超时 180 秒、后端 120 秒。

**长文实测（2026-10-19，源文 2102 字 → 小红书 / 公众号 / 抖音）**：

| 平台 | 适配后正文 | 格式 | 说明 |
|---|---|---|---|
| 小红书 | 874 字 | 通过 | 从 2102 字压缩到 1000 字上限以内 |
| 微信公众号 | 2161 字 | 通过 | 保留原文结构与段落 |
| 抖音 | 767 字 | 通过 | 口播脚本，只保留 5 个重点 |

- 首次测试时抖音输出 1242 字**超限**，说明"给上限"不足以约束长文改写；
  提示词改为"目标为上限的 85%，抖音脚本 ≤800 字，只讲 3-5 个重点"后复测通过。
- 三个平台一次 18.5 秒，`promptTokens=13000 / completionTokens=3593`，成本约 **0.027 元**。
- 源文末尾埋了"加我微信发你"作探针，三个平台的版本都把它删除了，合规预检均通过。

## 四、提示词设计

三层结构（`agent/prompts.py`）：

1. **系统提示 `ADAPT_SYSTEM_PROMPT`**：约束优先级最高，解决三件事
   - **不编造**：只能用原文的事实/数据/观点，不得新增功效承诺、价格、用户评价、个人经历；
   - **合规**：不得保留绝对化用语、站外引流、违禁品、低俗、未授权转载；
   - **形态**：遵守字数与标签规则，正文不超过 3000 字（跨平台改写是保留核心信息，不是搬运全文）。
   - 明确要求"话题标签只放 tags 字段，不要写进正文"。
2. **平台要点 `PLATFORM_HINTS`**：程序内置，决定输出长什么样（小红书钩子+分段、微博重点前置、
   抖音【画面】/【口播】、B站简介列看点、公众号小标题）。与数据库里的 `style_desc` 互补：
   `style_desc` 是管理员可改的风格要求，`PLATFORM_HINTS` 是平台形态。
3. **用户提示 `build_adapt_prompt`**：目标平台约束（上限、标签规则、风格）+ 源文章 + 输出 JSON 结构。

**输出契约**：

```json
{"title": "标题", "content": "正文", "tags": ["#话题1", "#话题2"]}
```

**为什么不把全部规则塞进改写提示词**：改写阶段的目标是"写得像这个平台"，不是"逐条对照规则"；
规则放在随后的合规预检里，既省 token，又避免模型为了规避规则把内容改得空洞。
改写提示词只保留最高风险的几类禁令（引流、功效、绝对化）。

**Mock 供应商**：`PROVIDER=mock` 时返回"截断到平台上限 + 固定标签"的确定性结果，
用于无 Key/断网时跑通整条链路（格式自检、落库、界面），不参与能力评价。

## 五、格式自检（程序，不交给模型）

`agent/format_check.py`：

| 检查项 | 规则 | 失败示例 |
|---|---|---|
| 标题长度 | `titleMaxLen > 0` 时 ≤ 上限；`=0` 表示无独立标题（微博），跳过 | "标题 24 字，超过上限 20 字" |
| 正文长度 | ≤ `contentMaxLen` | "正文 1200 字，超过上限 1000 字" |
| 标签数量 | 从 `tagRule` 文本解析 `N-M 个` / `N 个` / "不使用" | "标签 6 个，超过上限 5 个" |
| 标签格式 | 规则含"以 # 开头"或"#话题#"时，每个标签必须以 # 开头 | "标签需以 # 开头：小户型收纳" |
| 标签质量 | 非空、不含空格、不重复 | "标签「家居 好物」含空格" |
| 建议上限 | 正文超过 3000 字按句截断，并**记入 issues** | "正文 3500 字，超过适配建议上限 3000 字，已按句截断" |

**为什么必须程序算**：字数是可精确计算的，交给模型既浪费 token，又会让结论随模型状态波动。
自检结果确定，才能作为论文里"格式约束满足率"的量化指标。

**解析不出来的标签规则不检查数量**（宁可不报，也不误报）。管理员填 `tagRule` 时建议用
"N-M 个"或"不使用"的写法，页面已有示例。

## 六、适配后合规预检

复用阶段 5 的 `judge()`（`agent/judge.py`），不是另写一套：

- **规则按平台过滤**：主系统下发通用规则 + 所选平台的专属规则，每条带 `platformKey`；
  Agent 对每个平台取"通用 + 本平台"。
- **有兜底**：某平台一条规则都没匹配上时，按"平台规则 → 通用规则 → 全部规则"逐级回退。
  **绝不能出现"没有规则 → 直接通过"**，那比报错更危险。
- **标签也送检**：`content` 末尾附 `【话题标签】#...`，因为标签可能夹带引流词（如 #加微信）。
- **检索**：沿用 RAG（混合检索），规则少时直接全量下发；判定结果带 `hitRules` 与 `violations`。

**为什么必须复用**：如果预检和正式审核是两套逻辑，会出现"同一段文字，适配页说通过、
审核工作台说违规"的自相矛盾，人机协同的可信度会直接崩掉。

## 七、版本与留痕

`audit_adaptation` 每个平台一行：

| 字段 | 内容 |
|---|---|
| `article_id` / `platform_id` | 哪篇稿件的哪个平台 |
| `adapted_title` / `adapted_content` / `adapted_tags` | 适配产物（标签空格分隔） |
| `format_check` | 人可读摘要，如"通过｜标题 14 字，正文 268 字，标签 5 个" |
| `compliance_check` | "通过/疑似/违规/严重｜理由｜命中规则" |
| `version` | 同一稿件 + 同一平台的第几次适配，每生成一次 +1 |
| `adapted_by` / `create_time` | 操作人、时间 |

**为什么按"稿件 + 平台"而不是"稿件"计版本**：创作者可能只重新生成微博，不该让小红书的版本号也跳。
历史记录在页面上按时间倒序展示，可点"查看"回看完整内容并复制。

**写入安全**：标题 300 字、标签 300 字、摘要 1000 字按**码点**截断（避免把 emoji 的代理对切成半个字符）。

## 八、接口、权限与超时

| 接口 | 权限 | 说明 |
|---|---|---|
| `POST /api/article/{id}/adapt` | `creator:adapt` 或 `article:list` | body：`{"platformKeys": [...]}`，最多 5 个；不接受前端传正文 |
| `GET /api/article/{id}/adaptations` | 同上 | 适配历史 |

- **功能权限**由 `@SaCheckPermission` 控制；**数据权限**在服务层判断：非管理/审核角色只能适配自己的稿件。
- `platformKeys` 里的 `local` 会被拒绝（本平台是源，不是适配目标）。
- **超时分层**：Agent 内单次模型调用 25 秒；主系统适配客户端读超时 120 秒（审核仍是 30 秒，两类请求预算不同）；
  前端 axios 单独设为 180 秒。**不能沿用审核的 30 秒**，否则 5 个平台会把正常的慢请求误判成网络错误。

## 九、失败与降级

| 情况 | 行为 |
|---|---|
| Agent 不可用（网络/503/超时） | 返回 `agentFailed=true`，界面提示稍后重试；**不落库**，不阻断创作 |
| 某一个平台模型调用失败 | 整个请求返回 503（v1 的取舍：避免半套结果被误当成完整结果）。后续可改为逐平台部分成功 |
| 模型输出不是合法 JSON / 正文为空 | 422，日志保留原始输出前 600 字，便于排查 |
| 格式自检不通过 | **照常返回结果**，带 issues；不阻断，由创作者调整或重新生成 |
| 合规预检判违规 | 照常展示结论与修改建议；适配产物的处置权仍在人或后续审核流程 |

## 十、已知局限与后续

1. **不校验事实真伪**：只能约束"不新增原文没有的信息"，无法判断原文本身是否真实。
2. **平台规则会改版**：数值需人工维护；没有自动抓取（平台页面需要登录且结构不稳定）。
3. **适配质量尚未量化**：阶段 8 计划做格式满足率（已有）+ 人工评分（风格符合度/信息保留度/可读性）
   + LLM 评判与人工评分一致性。
4. **并发生成**：默认按平台并行（`ThreadPoolExecutor`，最多 4 个），短文本 3 个平台约 6 秒，
   2100 字长文约 9.6 秒；串行分别是 12.7 / 21.8 秒。代价是并发请求更多、遇到限流更容易触发 429，
   且当前实现中任一平台失败会让整个请求失败，没有做“部分成功”。实验数据见 `docs/实验-速度优化.md`。
5. **标签规则是自由文本**：靠约定格式解析，管理员写"建议若干"这类模糊描述时无法校验数量。
6. **合规预检按目标平台过滤规则，但规则库本身以本平台业务为基准**：平台专属规则需要持续补充。

## 十一、答辩可能追问的 5 个问题

1. **"你能真的发到小红书吗？"** —— 不能。个人开发者无发布接口，本功能止步于适配 + 预检 + 复制；
   论文里明确写了这个边界（D-M1）。
2. **"为什么微博写 2000 字不写 140？"** —— 140 是信息流展示长度，不是发布上限；2016 年起原创微博可发 2000 字。
   系统要求重点前置到前 140 字（WB-001 提示），不把展示限制误当发布限制。
3. **"格式检查为什么不用大模型？"** —— 字数/标签是确定性规则，程序算得准且免费；模型负责创作，
   程序负责验收，职责分离才能得到可复现的指标。
4. **"预检和正式审核会不会打架？"** —— 不会，两者调用同一个 `judge()`，只是触发场景和规则集合不同。
5. **"重复生成会不会越来越乱？"** —— 每次生成都留一条版本记录（稿件 + 平台维度递增），
   历史随时可回看，不会覆盖旧结果。
