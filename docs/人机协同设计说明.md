# 人机协同设计说明

> 阶段 7 交付物。对应代码：`AuditRecordService`、`ArticleServiceImpl.review`、
> `views/audit/workbench`、`views/audit/record`、`views/creator/article`（反馈弹窗）。
> 数据表：`audit_record`（智能体每次判定）、`audit_review`（审核员每次处理）。

## 一、目标与角色

**目标**：让智能体"初判"、审核员"终审"，每一次判定与改判都有据可查，
并把人工改判沉淀为下一轮评测的真实标注数据。

| 角色 | 在这个闭环里做什么 |
|---|---|
| 创作者 | 写稿 → 提交审核 → 看反馈（违规片段 + 修改建议 + 审核意见）→ 修改重提 |
| 智能体 | 对**当前这一版内容**给出 0/1/2/3 分级、理由、命中规则、违规片段与修改建议 |
| 审核员 | 运行初审 → 采纳或改判 → 终审通过/驳回/阻断；改判必须写原因 |
| 管理员 | 看全站判定分布、改判率、失败率；维护规则与平台约束 |

**两条必须守住的边界**：

1. **智能体不做处置**。删稿、封号、驳回一律由审核员执行（D-A7）；
2. **疑似（1）不是结论**，是"转人工"的信号。人工对疑似内容的任何决定都不算改判。

## 二、流程（两阶段介入 + 终审）

```
创作者：写稿 ──(可选) 发布前预检──> 提交审核
                                      │
审核员：打开工作台 ──> 运行智能体初审（POST_AUDIT）
                          │
                          ├─ audit_record 落库（每次一条，不覆盖）
                          │
                     查看等级/理由/规则/片段/建议
                          │
              ┌───────────┴───────────┐
              │                       │
          采纳（结论一致）          改判（结论不一致）
              │                       │（原因必填）
              └───────────┬───────────┘
                          ▼
                  audit_review 落库
                          │
                 稿件状态：通过 / 驳回 / 阻断
                          │
创作者：看反馈（片段高亮 + 修改建议 + 审核意见）→ 修改重提
                          │
             稿件内容变了 → 旧记录标记"过期"
                          │
                 重新初审 → 新一轮闭环
```

### 为什么初审放在工作台，而不是投稿时自动跑

- 投稿接口不能被模型拖慢：审核客户端 30 秒、失败还会重试，创作者会卡在提交按钮上；
- 审核员需要先看到"AI 说了什么"再决定，自动跑完再等人打开，结论可能已经过期；
- 失败可降级：智能体挂了不影响人工审核，工作台会显示一条"调用失败"的记录。

> 如果后续要做"提交即初审"，应改为异步任务 + 消息队列；本项目没有引入中间件（D-P5），
> 所以选择显式按钮触发，把可控性放在第一位。

## 三、数据落点

### audit_record（每次判定一条）

| 字段 | 说明 |
|---|---|
| `trigger_type` | 1 预检 / 2 发布审核 / 3 举报复审 / 4 适配预检；**只有 2 会进入工作台与改判统计** |
| `risk_level` | 0/1/2/3；`-1` 表示未成功判定（失败或人工补录） |
| `reason` / `hit_rule_codes` / `violation_fragments` / `suggestion` | 判定理由、命中规则、违规片段（JSON）、处置建议 |
| `model_name` / `prompt_tokens` / `completion_tokens` / `duration_ms` | 成本与性能数据；失败时 `model_name=agent-failed` |
| `content_hash` | **判定时稿件标题+正文的 SHA-256**，用于判断结论是否对应当前内容 |

失败也落库：审核员需要看到"这次没判成"，统计也需要失败率。人工补录的记录
`model_name` 为 `no-agent`（未运行）或 `content-changed`（内容已改），不计入"采纳/改判"。

### audit_review（每次人工处理一条）

| 字段 | 说明 |
|---|---|
| `audit_record_id` | 这次处理依据的是哪条智能体记录（NOT NULL，保证可追溯） |
| `action` | 1 采纳 / 2 改判 / 3 人工判定（无可用初判） |
| `final_level` | 0 通过 / 2 驳回 / 3 阻断 |
| `remark` | 处理意见；**改判时必填**，作为真实标注数据留存 |

## 四、采纳 / 改判的判定口径

| 智能体结论 | 审核员动作 | 记录为 |
|---|---|---|
| 0 通过 | 通过 | 采纳 |
| 0 通过 | 驳回 / 阻断 | **改判**（原因必填） |
| 1 疑似 | 通过 / 驳回 / 阻断 | **采纳**（疑似本来就是转人工，人工决定不算改判） |
| 2 违规 | 驳回 / 阻断 | 采纳 |
| 2 违规 | 通过 | **改判**（原因必填） |
| 3 严重 | 阻断 / 驳回 | 采纳 |
| 3 严重 | 通过 | **改判**（原因必填） |
| 失败 / 未运行 / 内容已改 | 任意 | 人工判定（不计入改判率） |

**改判率** = 改判 /（采纳 + 改判）。人工判定不计入分母，否则"智能体没跑"也会被算成
"人和 AI 不一致"，指标会失真。

## 五、结论过期：为什么用内容哈希而不是更新时间

稿件被修改后，旧的初审结论不能再用于采纳/改判。最初用
`audit_record.create_time < biz_article.update_time` 判断，验证时发现一个真实缺陷：

> 稿件修改与初审落在**同一秒**时，`DATETIME` 只到秒，比较结果为"未过期"，旧结论被误用。

改为 `content_hash`：初审时对"标题+正文"做 SHA-256 存进记录；读取反馈与审核时重新计算当前
内容的哈希，不一致就是过期。它不受时间精度影响，也顺带挡住了"改完又改回去"之外的误判
（改回去哈希相同，结论仍然有效，这是合理的）。

> 迁移脚本：`db/05_phase7.sql`（已建库用）；新装环境的 `02_schema.sql` 已包含该列。

## 六、界面

### 审核工作台（`/audit/workbench`）

- 左侧待审队列，右侧详情；
- **智能体初审卡片**：等级、模型、判定理由、命中规则、逐条违规片段与修改建议、
  处置建议、token/耗时；失败与过期各有明确提示；
- **审核处理**：通过 / 驳回 / 阻断；实时显示"与智能体建议：采纳 / 改判 / 疑似转人工"；
  改判时原因必填（前端提示 + 后端强制）；
- 保留敏感词基线作为对照（论文里的传统方案）。

### 创作者反馈（`/creator/article` → 查看反馈）

- 审核意见（驳回/阻断原因）；
- 智能体初审：等级、理由、逐条违规片段（高亮）+ 修改建议 + 处置建议；
- 审核员如何处理：采纳 / 改判 / 人工判定；
- "去修改"直接进入编辑页，修改后重提；重提后旧结论会被标记过期。

### 审核记录（`/audit/record`）

- 按触发场景、风险等级、只看改判筛选；
- 每条记录显示模型、token、耗时、人工处理与意见；
- 详情弹窗展示完整理由、违规片段与审核意见——论文原始数据可直接从这里导出/截图。

### 数据看板

- 审核员/管理员：智能体审核次数、改判率、改判次数、智能体失败数；
- 判定分布（通过/疑似/违规/严重/未判定）与人工处理分布（采纳/改判/人工判定）。

## 七、失败与降级

| 情况 | 行为 |
|---|---|
| 智能体不可用 | 工作台显示"调用失败"记录，审核员可直接人工审核；改判统计记为人工判定 |
| 模型输出不合法 | Agent 返回 422，主系统降级为失败记录，不阻断审核 |
| 审核员直接审核（没跑初审） | 后端自动补一条 `no-agent` 记录，审核意见仍可追溯 |
| 稿件在初审后修改 | 记录标记"已过期"，界面提示重新初审；后端也不会拿它算采纳/改判 |
| 审核员审核自己的稿件 | 拒绝（利益冲突隔离） |

## 八、统计与论文价值

系统已经能直接给出：

- 智能体判定分布（0/1/2/3 + 失败）；
- 人工采纳率、改判率、人工判定占比；
- 每条判定的 token、耗时、模型（成本与性能）；
- 改判原因的原始文本（可作为错误分析与下一轮规则的输入）。

**注意**：改判率不是"越低越好"。智能体判疑似、人工接手是设计内的流程；
只有"通过↔违规"的翻转才是真正的分歧。论文里应同时报告采纳率与分歧明细，
不能只报一个百分比。

## 九、局限与后续

1. **只有一个审核员账号**，改判率是单人数据，不能代表多人一致性；后续可多账号对比。
2. **没有"同一稿件的版本对比"界面**，但 `audit_record` 已保留每次判定与内容哈希，
   数据足够，界面可后续补。
3. **没有审核时效统计**（从提交到处理多久），字段都在，属于看板增强项。
4. **改判原因是自由文本**，暂未做原因分类；阶段 8 可人工归因（规则缺失/语境误判/模型过严等）。
5. **初审是显式按钮**，不是提交即触发；这是无消息队列下的取舍（见第二节）。

## 十、答辩可能追问的 5 个问题

1. **"AI 判错了怎么办？"** —— 审核员改判，原因必填；改判记录进入 `audit_review`，
   下一轮可以据此补规则或调提示词。
2. **"AI 判违规、人判通过，算不算改判？"** —— 算，这是最需要关注的分歧；原因会留痕。
3. **"AI 判疑似、人判违规，算改判吗？"** —— 不算。疑似是"转人工"信号，人工决定是流程内动作。
4. **"稿件改了，旧结论还会被用吗？"** —— 不会。用内容哈希判断，改过即过期；
   同一秒内修改也能识别（时间比较做不到）。
5. **"改判率能说明什么？"** —— 说明人机分歧的量级与方向；要结合分歧明细看，
   不能把"疑似转人工"当成 AI 的错误。
