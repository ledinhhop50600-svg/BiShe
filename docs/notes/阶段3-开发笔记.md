## 二、内容生命周期（本阶段的核心逻辑）

```
创作者写稿
  └─ 保存草稿（状态 0）
      └─ 提交审核（状态 1）── 撤回 ──> 回到草稿
          └─ 审核员处理
              ├─ 通过   → 已发布（状态 2）── 下架 ──> 已下架（状态 5）
              ├─ 驳回   → 已驳回（状态 3）── 修改后重新提交 ──> 回到待审核
              └─ 阻断   → 已阻断（状态 4，严重违规）
                          └─ 被举报且举报成立 → 已下架
```

**两条关键设计约束**：

1. **状态不由前端设置**。前端没有任何接口可以直接把稿件状态改成"已发布"，只能调用 `submit / withdraw / review / offline` 这些**动作接口**。接口内部校验当前状态是否允许该动作 —— 这就是"状态机"的落地方式。实测：已提交的稿件再次提交会被拒绝；草稿直接审核也会被拒绝。
2. **功能权限与数据权限分开**。功能权限（能不能调这个接口）由 `@SaCheckPermission` 控制；数据权限（能不能动这篇稿件）在服务层判断。实测：另一位创作者查看他人稿件详情返回 403；创作者调用后台稿件列表也返回 403。

## 三、敏感词基线的真实效果（实测数据）

用一段典型违规文案做检测：

```
输入：全网最低价的美肤面膜，三天见效不是梦，需要的姐妹加我微信领取清单。
结果：命中 3 个词（全网最低价 / 三天见效 / 加我微信），最高等级"违规"，
      类别：广告法、虚假宣传、引流诱导
```

但它也会误判。同一套词库检测：

```
输入：最近在看《最好的我们》，很推荐。
结果：命中「最好」→ 判为违规
```

**这是关键词匹配的固有限制：它只看"有没有这个词"，不理解语境。**
这个反例已经写进敏感词库页面的检测工具里，答辩时可以直接现场演示 —— 它是引入智能体的最直接理由，也是阶段 8 对比实验的起点。

> 一个过程插曲：这个反例最初**测不出效果** —— 词库里有「最佳」「最高级」却没有「最好」，所以《最好的我们》根本不命中。
> 我是在验证时发现的，随后把「最好」补进词库（它本来就是广告法禁止的绝对化用语），并实测确认命中才留下这段文案。
> **教训：演示用的文案和例子必须实测，不能想当然。**

## 四、踩到的坑

### 坑 1：模板编译错误 —— 把 `#header` 插槽嵌进了 `v-if` 里

- **现象**：`npm run build` 报 `TypeError: Cannot read properties of undefined (reading 'type')`，指向审核工作台页面。
- **原因**：我写成了 `<el-card><template v-if="selected"><template #header>…</template>…</template></el-card>`。
  具名插槽必须是组件的**直接子节点**，嵌在 `v-if` 模板里会让 Vue 编译器拿到畸形的 AST 而崩溃。
- **修复**：把 `#header` 提到 `el-card` 的直接子节点位置，`v-if` 放到插槽内部。
- **教训**：**`npm run build` 是最便宜的静态检查**。开发服务器（dev）遇到这类模板错误往往是"页面白屏 + 控制台报错"，不容易定位；而生产构建会直接把出错的文件和位置指出来。每阶段结束跑一次构建应该是固定动作。

### 坑 2：设计缺口 —— 举报没有触发入口

- **现象**：举报处理页和接口都做好了，但创作者在系统里**根本找不到"别人已发布的内容"**，也就无从举报。
- **原因**：系统是管理后台形态，没有面向浏览的内容列表；而举报的对象必然是"他人的已发布内容"。
- **修复**：新增「内容广场」页面（创作者可见他人已发布内容，可发起举报），并在种子数据里加上对应菜单与角色授权。
- **附带收获**：这次加菜单只改了**数据**（`sys_menu` + `sys_role_menu`），没有改任何前端代码，侧边栏就多出了这一项 —— 正好是"菜单由数据库驱动"的实证，答辩时可以举例。

### 坑 3：浏览器工具 webview 不可用，无法做 UI 端到端

- **现象**：本阶段尝试浏览器自动化验证时，工具持续报 `browser guest not attached (webview not ready)`，重试多次无效（阶段 2 时它是可用的）。
- **处理**：改用两项更硬的验证替代：
  1. **接口层全流程脚本** `tools/verify_stage3.py`（创建→提交→驳回→重提→通过→举报→下架，含越权与状态机拒绝）；
  2. **生产构建** `npm run build`（验证所有页面的模板与引用都能编译）。
- **如实说明**：本阶段的页面**没有经过浏览器点击验证**。页面的结构与交互沿用阶段 2 已实测通过的模式（列表+弹窗+表单），且接口路径已与后端逐一核对；但"页面在浏览器里点的效果"仍建议在下次环境可用时补一次人工走查。

## 五、你必须能讲出来的 3 件事

1. **稿件状态为什么前端改不了**：状态只能通过"提交/撤回/审核/下架"这些动作接口流转，每次动作都会校验当前状态是否允许 —— 这样前端无法绕过审核直接发布。
2. **敏感词匹配和智能体审核的区别（用《最好的我们》举例）**：关键词匹配只知道"出现了哪个词"，会把作品名误判；智能体能结合语境判断，并给出规则依据、违规片段和修改建议。
3. **为什么要先冻结接口契约**：主系统围绕两个 HTTP 接口（审核、适配）设计，Agent 独立开发、独立测试、可随时换模型或框架，不牵动主系统。
