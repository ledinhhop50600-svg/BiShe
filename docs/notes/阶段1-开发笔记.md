## 二、认证这条链路是怎么走的（本阶段最该理解的部分）

### 1. 登录

1. 前端 `Login.vue` 提交账号密码 → `stores/user.js` 调用 `api/auth.js`
2. Axios 请求 `/api/auth/login` → Vite 代理转发到后端 8080
3. `AuthController.login` → `AuthServiceImpl.login`：
   - 按账号查用户（查不到和密码错**返回同一句提示**，避免被用来试探有哪些账号）
   - 用 `passwordEncoder.matches(明文, 哈希)` 校验密码
   - 检查 `status`，禁用账号不允许登录
   - `StpUtil.login(userId)` 签发令牌
   - 返回令牌 + 用户信息（含角色、权限、菜单树）
4. 前端把令牌存进 `localStorage`，之后每个请求由拦截器自动带上（请求头名 `satoken`）

### 2. 拦截

`SaTokenConfig` 注册了拦截器：除白名单外，所有 `/api/**` 都要求已登录。
未登录会抛 `NotLoginException`，被 `GlobalExceptionHandler` 转成 `code=401`；前端响应拦截器看到 401 就清掉本地令牌并跳回登录页。

**白名单只有两个**：`/api/auth/login`（登录本身）和 `/api/health`（启动脚本用它判断服务是否就绪）。

### 3. 动态菜单与权限

- 用户能看到的菜单 = `sys_user_role` → `sys_role_menu` → `sys_menu` 三次关联的结果
- 菜单表里 `menu_type = 'F'` 的记录是**按钮级权限**（如 `audit:rejudge` 改判），不进入菜单树，只参与权限校验
- 后端 `StpInterfaceImpl` 向 Sa-Token 提供"某用户的角色与权限列表"，之后接口上写 `@SaCheckPermission("...")` 即可鉴权
- 前端 `userStore.hasPermission('article:edit')` 用来控制按钮是否显示

### 4. 密码为什么不能存明文

数据库里存的是 **BCrypt 加盐哈希**：单向不可逆，且同一个密码每次生成的哈希都不同（内含随机盐），无法通过比对哈希值反推密码。校验用 `matches(明文, 哈希)` 而非解密。
生成种子数据时用 `PasswordHashPrinter` 算出了 `123456` 的哈希（自校验通过），四个演示账号共用。

## 三、踩到的坑

### 坑 1：端口被旧实例占用，且旧实例杀不掉

- **现象**：后端重启失败，日志 `Web server failed to start. Port 8080 was already in use`；而访问 `/api/health` 返回的不是我们的 `Result` 格式 —— 说明响应的是**旧版本实例**。
- **排查**：`netstat -ano | grep :8080` 找到 PID → `taskkill /PID xxx /F` 报"**拒绝访问**"，PowerShell 的 `Stop-Process` 同样被拒（连关掉沙箱执行也一样）。
- **结论**：由 `start.bat` 的 `start` 命令拉起的窗口进程，其权限上下文与我的执行环境不同，**我无法终止它们**。
- **处理**：改用"绕开"策略 —— 在自己的会话里把后端跑在 8082、前端跑在 5174 完成验证；随后确认用户环境已自行更新到新代码（旧进程已退出、脚本用新代码重新拉起）。
- **给以后的提示**：**开发期由我在自己的会话里启动服务**（便于控制与看日志），`start.bat` 只用于整体验证与交付给用户使用。若用户要重启，先关闭对应窗口再双击脚本。

### 坑 2：`start.bat` 的就绪检查指向了已删除的接口

- **现象**：阶段 0 的 `/api/ping` 在本阶段随 `demo_ping` 临时表一起被删除，脚本里的就绪检查会永远失败。
- **处理**：新增 `/api/health`（不依赖数据库、无需登录）作为健康检查接口，脚本改用它。

### 坑 3（小）：脚本"已在运行则跳过"的判断被我误判为失效

- **现象**：测试时脚本输出"启动后端"，我一度以为端口检测逻辑写错了。
- **排查**：单独写了一个最小脚本验证 `netstat -ano | findstr ":8080" | findstr "LISTENING" >nul` 的返回值 —— 端口被占用时 `errorlevel=0`、空闲时为 `1`，逻辑**正确**。
- **真实原因**：那一刻旧进程刚好已退出、端口确实空闲，脚本判断是对的。
- **经验**：**怀疑某段逻辑之前，先用最小脚本单独验证它**，不要凭一次整体运行的观感下结论。

## 四、你必须能讲出来的 3 件事

1. **登录之后发生了什么**：服务端校验密码 → 签发令牌 → 前端存下令牌 → 之后每个请求由拦截器自动带上 → 服务端每次靠令牌认出"你是谁"。
2. **为什么不同角色看到的菜单不一样**：菜单不是前端写死的，而是后端按「用户 → 角色 → 菜单」三次关联查出来的；按钮级权限（如"改判"）用同一套机制控制。
3. **密码为什么安全**：数据库存的是 BCrypt 加盐哈希，不可逆；校验是"拿明文算一遍再比对"，不是解密。
