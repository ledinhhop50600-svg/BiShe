## 二、权限体系的三层结构（本阶段最核心的设计）

答辩时如果只讲一层，就会被追问"能不能绕过"。正确的讲法是**三层独立防线**：

```
第 1 层  前端路由守卫    → 页面级：没权限的页面直接跳 403（体验层）
第 2 层  按钮指令 v-perm  → 元素级：没权限的按钮不渲染（体验层）
第 3 层  后端 @SaCheckPermission → 接口级：没权限的请求返回 403（真正的安全边界）
```

**为什么说前两层只是"体验层"**：前端代码运行在用户的浏览器里，用户完全可以改前端代码或直接手工调接口。所以前两层的作用是"让不该看到的人看不到入口"，**真正的拦截必须在后端**。

实测证据（`verify_stage2.py` 第 2 组）：用审核员、创作者账号直接调用户管理 / 角色管理 / 菜单管理接口，**6 项全部返回 403**。

### 一个容易被追问的设计点：为什么前端路由是静态的？

菜单树来自数据库，但路由表写在前端。原因是：**路由要绑定具体的 Vue 组件文件，而组件是代码资产，不可能由数据库凭空生成**。数据库决定的是"哪些菜单可见、哪些页面可进"，两者结合才是完整的动态权限：

- 菜单项：完全由后端下发的菜单树渲染（前端没写死任何一项）
- 页面能否进入：路由用 `meta.perms` 声明所需权限，守卫比对当前用户的权限列表
- 接口能否调用：后端注解校验

### 权限数据的流向

```
管理员在「角色管理」勾选权限
   → 写入 sys_role_menu（角色-菜单关联表）
   → 该角色的用户下次登录时，/api/auth/me 返回新的菜单树与权限列表
   → 侧边栏、可进入的页面、可点的按钮同时变化
```

**全程不需要改代码、不需要重启服务** —— 这是答辩演示时最有说服力的一步。

## 三、踩到的坑

### 坑 1：权限回显失效（有数据丢失风险，最严重的一个）

- **现象**：打开「分配权限」弹窗时，角色**已有的权限没有被勾选**，界面显示"全空"。此时管理员若直接点保存，会把该角色的权限全部清掉。
- **排查过程**（走了弯路，值得记）：先怀疑接口没返回数据 → 在浏览器里直接调 `/api/role/3/menuIds`，返回 `[1,40,41,42,43]` 正常；再怀疑勾选时机太早，改用 el-dialog 的 `@opened` 事件后仍无效；最后逐层打印 Vue 组件实例，才发现**浏览器执行的是旧代码**（见坑 2），修复代码根本没跑起来。
- **真正的修复**：`default-checked-keys` 只在 el-tree **创建时**生效，复用同一个树实例切换角色时不会更新。改为给 el-tree 加 `:key="treeKey"`，每次打开弹窗时让 key 变化，强制重建树。
- **验证**：重建后用脚本读取 DOM，创作者角色精确勾选了 5 项（数据看板、创作中心 + 我的稿件/去投稿/跨平台适配），与数据库中的 `[1,40,41,42,43]` 完全一致。截图见 [阶段2-角色分配权限.png](../assets/阶段2-角色分配权限.png)。

### 坑 2：改了代码但浏览器不生效 —— 重复的前端服务 + 陈旧模块

- **现象**：文件确认已改、服务端返回的代码也是新的，但浏览器行为始终是旧逻辑。
- **根因**：机器上同时跑着**两个前端开发服务**（5173 和 5174，后者是早前调试遗留的），浏览器加载的模块来自其中之一，模块缓存与文件改动不一致。
- **处理**：清掉所有前端服务，只保留一个，并用**全新标签**重新验证 —— 一次通过。
- **经验（两条都很有用）**：
  1. **怀疑业务代码之前，先确认"服务端返回的代码是不是新的"**（`curl` 一下模块内容就能看出来），否则会在错误的地方浪费大量时间。
  2. **Vue 会把所有已声明的 prop 都放进组件的 props 对象**（未传的值为 undefined）。所以"能在 props 里看到某个 key"并不代表"我传了值" —— 判断 prop 是否生效要看**值**，不是看 key 是否存在。

### 坑 3：浏览器自动化环境的点击与截图失效

- **现象**：用浏览器工具做端到端测试时，填写表单正常，但**真实点击超时**、**截图也超时**（`browser screenshot surface preparation timed out`）。
- **判断**：填写是 DOM 层操作、点击与截图需要渲染/合成层参与 —— 渲染层出问题，是**测试工具环境的问题，不是项目代码的问题**（真实用户用鼠标点击不受影响）。
- **处理**：改用页面内 JS 触发点击（`el.click()`）继续完成验证，并在笔记里如实记录这个限制。

### 坑 4（我自己的操作失误）

写文件时路径少打了一个 `+`（`毕设-基于SpringBootVue...`），在 E 盘根目录创建了一个多余目录，文件写到了错误位置。
**改进**：写文件后立刻用 `ls`/`find` 核对落点；`git status` 也能暴露异常（阶段提交时发现过）。

### 坑 5：逻辑删除 + 唯一索引 = 账号名被永久占用（重跑验证才暴露）

- **现象**：接口验证脚本第一次运行全部 PASS；过一段时间**重跑同一个脚本**，却在"新增用户"这步失败，报的是数据库错误。
- **根因**：`sys_user.username` 上有唯一索引；用户被**逻辑删除**后记录仍在表里（`deleted = 1`），而**唯一索引对已删除的记录同样生效** —— 这个账号名就再也无法被使用。更隐蔽的是：应用层的账号查重走 MyBatis-Plus 的自动过滤（只查 `deleted = 0`），所以查重通过、插入时却撞上唯一约束，抛出的是一句前端看不懂的 SQL 错误。角色的 `role_key` 有完全相同的问题。
- **修复**：逻辑删除**之前先改名**（`原名#del<id>`）再删除 —— 既释放了名字，又保留"这个名字曾属于谁"的可追溯信息。实测连续两次运行验证脚本均 PASS，证明账号名可复用。
- **为什么这条最值得记**：**这类问题只有"重复运行验证"才会暴露** —— 第一次运行一定是通的。所以验证脚本必须设计成可重复运行，跑通一次不等于没问题。

## 四、你必须能讲出来的 3 件事

1. **权限的三层防线，以及为什么前两层不算安全边界**：路由守卫和按钮指令让不该看到的人看不到入口；真正的拦截是后端的权限注解，实测越权调用接口会被拒绝（403）。
2. **改权限不用改代码**：管理员在角色管理里勾选菜单 → 写入关联表 → 该角色用户重新登录后菜单、页面、按钮同时变化。
3. **为什么前端路由是静态的、而菜单是动态的**：路由要绑定组件文件（代码资产），菜单可见性与页面可进入性由数据库决定，两者结合实现动态权限。
