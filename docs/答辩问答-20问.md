# 答辩问答 20 问

> 用法：每题先记"一句话结论"，再记 2-3 个支撑数字。不要背长段，答辩时按结论展开。
> 更详细的数据在括号里的文档中。

## 1. 你的创新点是什么？

一句话：**不是加一个聊天框，而是让单智能体真正参与内容审核与跨平台适配这两条业务链**。

具体三件事：
- 智能审核：六类规则、四级分级、RAG 检索、可追溯到规则编号；
- 跨平台适配：按平台改写 + **程序做格式自检** + 复用审核规则做合规预检；
- 人机协同：AI 初判、审核员终审，采纳/改判全部留痕，改判率可统计。

（详见 `docs/系统功能说明.md`、`docs/人机协同设计说明.md`）

## 2. 为什么用 SpringBoot + Vue？为什么智能体用 Python？

导师指定 SpringBoot + Vue；这两个也是国内业务系统最常见、资料最多的组合。
智能体单独用 Python + FastAPI：LangChain/向量库/模型 SDK 的生态在 Python 更成熟，
而且独立服务可以单独重启、单独换模型，不拖累主系统。

代价是多了一个进程和一层 HTTP 契约，所以我把接口字段冻结成
`docs/Agent接口契约-v1.md`，两边按契约开发。

## 3. 为什么是单 Agent，不是多 Agent？

这个任务的边界很清楚：**输入是一篇内容 + 一组规则，输出是一个结构化判定**，
不需要多个角色互相辩论。多 Agent 会带来编排、通信、成本、调试复杂度，
而收益在这个任务上不明显。

但我预留了扩展：Agent 内部是"工具注册表"结构（检索、定位、判定都是步骤），
表结构也预留了多平台/多规则；以后要做"审核 Agent + 适配 Agent + 投诉复核 Agent"，
不需要推翻现有接口。

（D-A2/D-A3，见 `docs/decisions-agent.md`）

## 4. 这和直接调大模型 API 有什么区别？

直接调 API 只是"给一段文字、问它违不违规"。系统做了四件 API 之外的事：
1. **上下文**：从数据库取规则、平台约束、敏感词，组装成契约请求；
2. **检索**：规则多时先召回最相关的若干条（RAG），而不是全塞；
3. **约束**：分级策略、长文逐段、片段必须原文真实存在、最多 8 处；
4. **工程化**：超时分层、失败降级、回放缓存、结果落库、人工复核。

## 5. RAG 具体怎么做的？为什么不把规则全塞进去？

- 规则向量化用免费 bge-m3（硅基流动），规则文本按 `code:content-hash` 缓存；
- 检索是**混合**的：元规则（商业属性判定）强制带上 + 词面命中（规则示例词/敏感词）+ 分段向量召回；
- 长文按 300 字分段，最多 20 段，再和规则算相似度；
- top_k=6。

不全塞的原因：规则一多，提示词变长、成本上升、模型注意力被稀释；
实测全量规则（D）token 比 RAG（C）多 38%，四级精确匹配反而更低（86% vs 89%）。

（`docs/实验-对比实验-v4-放宽口径.md`）

## 6. 为什么用 deepseek-flash？更贵的模型不是更好吗？

同一评测集上，**更贵的 v4-pro 反而更差**：B 65 / C 73 / D 79，
而 flash 是 78 / 85 / 83。原因是 pro 为深度推理优化，审核任务关闭思考模式后反而失去优势；
flash 本身就是面向快速判定优化的。

所以选型结论是"**这个任务上 flash 更合适**"，不是"贪便宜"。
（`docs/实验-模型对比-pro.md`）

## 7. 四级分级怎么定？"疑似"到底算不算违规？

- 0 通过；1 疑似；2 违规；3 严重；
- **先判内容性质**：商业推广还是个人分享。广告法类规则只对商业内容按建议等级判；
  个人分享里的夸大表述判"疑似"，转人工；
- 站外引流、违禁品、明显侵权不放宽。

"疑似"不是违规，是**转人工**的信号：不阻断发布，人工通过或驳回都不算改判。
这样既避免误杀个人分享，又不放过真正的商业违规。

（D4 决策与实测，见 `docs/待优化清单.md`）

## 8. 人机协同怎么闭环？改判率怎么算？

流程：投稿 →（可选）AI 预检 → 提交 → 审核员运行 AI 初审 → 采纳/改判 → 终审 →
创作者看反馈修改 → 重提 → 旧结论过期 → 重新初审。

改判率 = 改判 /（采纳 + 改判）。口径：
- AI 说通过/疑似，人驳回/阻断 → 改判；
- AI 说违规/严重，人通过 → 改判；
- **AI 说疑似，人工怎么处理都不算改判**（本来就是转人工）；
- 没跑 AI / AI 失败 / 内容已改 → 人工判定，不进分母。

（`docs/人机协同设计说明.md`）

## 9. AI 判错了怎么办？

三道防线：
1. **分级从宽**：拿不准给"疑似"，不直接阻断；
2. **人工终审**：审核员可以采纳、改判、驳回，改判必须写原因；
3. **留痕可分析**：每次判定（含失败）都写 `audit_record`，每次人工处理写 `audit_review`，
   改判原因成为下一轮补规则/调提示词的依据。

## 10. 怎么保证 AI 不瞎编、结论可追溯？

- 提示词要求"只能依据提供的规则，命中的规则必须给编号"；
- 违规片段必须是原文中真实存在的连续文字，不能改写/拼接；
- 返回 `hitRules`（规则编号 + 名称 + 来源）与 `violations`（片段 + 问题 + 建议）；
- 规则库每条都有 `source`（法规/平台规范条款），答辩可以逐条溯源；
- 评测里专门统计"违规片段有效率"（当前 100%）与"规则召回"。

## 11. 内容改了，旧结论怎么处理？

用**内容哈希**：初审时对"标题+正文"做 SHA-256 存进 `audit_record.content_hash`；
读取反馈或人工审核时重新计算当前内容的哈希，不一致就是过期。

为什么不用 `update_time`：MySQL DATETIME 默认只到秒，**同一秒内修改并重提**时
时间比较会失效（这是实测发现的真实缺陷）。哈希不受时间精度影响。

（`docs/notes/阶段7-开发笔记.md`）

## 12. 跨平台适配怎么保证格式？

字数、标签数量、标签格式这些**客观约束由程序算**，不交给模型：
- 标题/正文长度、标签数量与格式、重复/空格标签；
- 超限给明确 issues，不静默通过；
- 模型只负责"写得像这个平台"，程序负责验收。

另外提示词给"目标长度为上限的 85%"，因为实测模型对长文容易超限
（2102 字的小红书版本曾输出 1111 字，超 1000 上限）。

（`docs/适配规则与提示词设计说明.md`）

## 13. 为什么不做真实发布？

个人开发者拿不到各平台的发布接口：微信公众号个人号发布权限已回收、抖音需要企业资质、
小红书没有公开 API。硬做只能模拟，反而不真实。

所以把价值放在**适配 + 预检**：生成的版本可以直接复制粘贴，格式和合规问题提前发现。
这个边界我在开题和论文里都明确写了（D-M1）。

（`docs/decisions-multiplatform.md`）

## 14. 平台字数限制怎么来的？微博到底 140 还是 2000？

逐个核对公开创作规范：
- 小红书 20 字标题 / 1000 字正文；公众号 64 / 20000；抖音 55 / 1000；
- **微博 2016 年起原创微博上限 2000 字**，140 是信息流展示长度，不是发布上限。
  所以系统把上限设为 2000，同时要求"重点放在前 140 字"；
- B站按**视频投稿**（80 / 2000），专栏是另一套规格（40 / 200-20000），不混用。

平台会改版，数值在数据库里，管理员可改。

## 15. 长文本怎么处理？成本和耗时？

- 审核：长文逐段检查，最多 8 处违规；关键词定位模式先聚焦到命中规则的段落，
  没有命中就回退全文（避免"没命中=通过"）；关闭 DeepSeek 思考模式后，
  长文不再出现空输出，成本降 55%、耗时降 60%；
- 适配：目标长度为上限的 85%，超 3000 字按句截断并记 issue；
- 实测 2102 字适配 3 个平台约 18.5 秒、约 0.027 元。

## 16. 评测集怎么构建？κ=0.51 怎么解释？

- 52 条 = 自建 28 条（分层：易/陷阱/盲区/边界/多类/长文/正常）+ ToxiCN 24 条（正负各 12）；
- 自建样本按区分度设计，专门做"含违禁词但语境合法""无关键词但违规"这类陷阱；
- 标注一致性：15 条争议样本盲评，四级 Cohen's κ = 0.51（中等一致），
  分歧 5 条按统一口径裁决后重跑。

κ=0.51 不算高，我在论文里如实写"单人标注、样本量小"的局限，不把它包装成高一致性。

（`docs/标注一致性报告.md`、`tools/eval_set/README.md`）

## 17. 实验里 B 的准确率最高，为什么还选 C（RAG）？

这是答辩最容易被问的点。结论：**"谁更准"取决于判定口径，不是模型本身**。
- 严格口径（v3，历史）：C 85% > D 83% > B 78%；
- 放宽口径（v4，2026-10-29 复测）：B 81% > D 79% > C 75% > A 58%；
- 单轮 1–2 个百分点的差异不应说成稳定优势；排序翻转主要来自 5 条标签变更。

选 C 的理由是**与策略无关**的三条：
1. **可审计**：规则引用召回 C 48% / D 61% / B 0%，审核员终审要看到依据；
2. **策略可调**：改规则立即生效，不用改提示词，这是按平台预检的基础；
3. **人工兜底下偏保守是安全方向**：误报转人工，漏报才上线。

（`docs/实验-对比实验-v4-放宽口径.md`）

## 18. 系统安全怎么做的？

- 登录：Sa-Token，BCrypt 密码，账号禁用检查；注册有一次性算式验证码；
- 权限三层：路由守卫（页面）、`v-perm`（按钮）、`@SaCheckPermission`（接口，真正的边界）；
- 数据权限：创作者只能操作自己的稿件；审核员不能审自己的稿件；
- 密码字段 `@JsonIgnore`，不会出现在接口返回；
- `.env`、`.replay` 不进 Git；
- 未登录 401、越权 403、业务失败统一返回结构。

（`docs/测试用例与执行记录.md`）

## 19. 数据库设计有什么取舍？

- 16 张表：5 张系统权限 + 5 张业务 + 6 张审核/适配；
- **不加外键**：便于分批导入种子数据、避免批量操作锁等待；关系由程序保证（要能说清这个取舍）；
- **逻辑删除**：用户/角色/稿件保留 `deleted`，可追溯；用户名删除时重命名避免唯一索引冲突；
- **状态用数字**并写注释，状态流转只走动作接口，前端不能直接改状态；
- `audit_record` 每次判定一条、不覆盖；`audit_adaptation` 按稿件+平台版本递增。

（`docs/数据库设计文档.md`）

## 20. 系统局限与后续工作？上线要改什么？

局限：
- 不真实发布、只做文本；平台规则需人工维护；
- 评测集 52 条、人工评分单人且全 5 分，统计显著性有限；
- 适配长文偶发超限；审核多类混排召回不全；
- 没有并发/多租户/监控。

上线要补：HTTPS 与更强的鉴权、限流与防刷、异步任务（提交即初审）、
对象存储（图片/视频）、多租户与审计日志、平台规则订阅与版本化、
内容安全合规评估、成本与可用性监控。

**一句话收尾**：这个系统的价值不是"AI 什么都能判对"，而是
**把 AI 放进一个有约束、可追溯、可纠正的业务流程里**。
