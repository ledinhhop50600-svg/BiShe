# 数据库设计文档

> 阶段 1 产出物。对应脚本：[db/02_schema.sql](../../db/02_schema.sql)（建表）、[db/03_seed.sql](../../db/03_seed.sql)（种子数据）。
> 用途：答辩时逐张表讲清"存什么、为什么这么设计"；也是论文「数据库设计」章节的素材。

## 一、总体设计

- 数据库：MySQL 8.0.46，库名 `zimeiti`，字符集 **utf8mb4**（支持 emoji，稿件正文里会出现）
- 存储引擎：全部 InnoDB
- 共 **16 张表**，按职责分三组：

| 分组 | 表 | 职责 |
|---|---|---|
| `sys_*`（5 张） | sys_user、sys_role、sys_menu、sys_user_role、sys_role_menu | 用户、角色、菜单与权限（RBAC） |
| `biz_*`（5 张） | biz_article、biz_category、biz_tag、biz_article_tag、biz_report | 稿件内容与举报 |
| `audit_*`（6 张） | audit_platform、audit_rule、audit_record、audit_review、audit_sensitive_word、audit_adaptation | 智能体审核与跨平台适配（为阶段 5～8 预埋） |

### 表间关系

```
sys_user ──< sys_user_role >── sys_role ──< sys_role_menu >── sys_menu
   │                                  （用户-角色-菜单：动态菜单与权限的数据来源）
   │
   │  author_id
   ├────────< biz_article ──< biz_article_tag >── biz_tag
   │               │  │  │
   │               │  │  └──< biz_report           （举报：谁举报了哪篇稿件）
   │               │  │
   │   reporter_id │  │  article_id
   │               │  └──< audit_adaptation >── audit_platform
   │               │        （一篇稿件适配到某个目标平台的产物）
   │               │
   │               └──< audit_record ──< audit_review
   │                    （智能体的每次判定 + 审核员的复核改判）
   │
   └── audit_rule ──> audit_platform   （规则可归属某个平台；为空表示通用规则）
```

## 二、设计原则（答辩会被问到的几处）

1. **逻辑删除**：业务主表（用户、角色、稿件）用 `deleted` 字段标记删除，不做物理删除。
   原因：平台数据需要可追溯 —— 被"删除"的稿件与用户，将来若涉及纠纷或审计仍要能查证。MyBatis-Plus 的 `@TableLogic` 让查询自动过滤，业务代码无需关心。
2. **状态用数字编码并写进注释**：如稿件 `status`：0 草稿 / 1 待审核 / 2 已发布 / 3 已驳回 / 4 已阻断 / 5 已下架。
   原因：数字比字符串省空间、比较快，配合注释与枚举类依然清晰。
3. **不加外键约束**：表间关系由程序保证，不建 FOREIGN KEY。
   原因：便于分批导入种子数据与后续维护；外键在批量操作时容易造成锁等待。这是国内业务系统的常见取舍，**但要能说清这个取舍**。
4. **权限数据全在数据库**：用户能看到哪些菜单、能点哪些按钮，由 `sys_role_menu` 决定，不在代码里写死。
   原因：改权限只需改数据，不用改代码、不用重新部署。
5. **规则库按平台维度组织**：`audit_rule.platform_id` 为空表示通用规则（所有平台适用），有值表示某平台的专属规则。
   原因：同一篇内容发到不同平台，规则并不相同（例如站外引流在小红书属违规、在其他平台可能只是提示），这正是"按目标平台分别审核"的数据基础。
6. **审核记录与适配记录单独成表**：不把智能体的判定结果直接写进稿件表。
   原因：同一篇稿件会被审核多次（发布前预检、发布后审核、举报复审、适配预检），需要保留每次判定的完整痕迹用于评测与追溯。稿件表只保留"当前状态"（`status`、`risk_level`、`reject_reason`）。

## 三、逐张表说明

### 系统与权限

| 表 | 存什么 | 关键字段与说明 |
|---|---|---|
| **sys_user** | 用户账号 | `username` 唯一；`password` 存 BCrypt 哈希（**数据库里看不到明文**）；`status` 0 禁用 / 1 启用（禁用后无法登录）；`deleted` 逻辑删除 |
| **sys_role** | 三种角色 | `role_key` 是程序判断用的标识（admin / reviewer / creator），`role_name` 是界面显示的中文名。用两个字段分开，改显示名不会影响程序逻辑 |
| **sys_menu** | 菜单 + 按钮权限 | `menu_type`：M 目录 / C 菜单页面 / F 按钮权限；`perms` 是权限标识（如 `article:list`），后端接口用它校验；`parent_id` 表达层级 |
| **sys_user_role** | 用户属于哪些角色 | 联合唯一索引 `(user_id, role_id)`，防止重复授权 |
| **sys_role_menu** | 角色能看到哪些菜单与按钮 | 动态菜单的数据来源。三种角色的差异全在这张表里 |

### 业务内容

| 表 | 存什么 | 关键字段与说明 |
|---|---|---|
| **biz_article** | 稿件（系统核心业务对象，也是智能体的审核对象） | `content` 用 LONGTEXT（长文）；`status` 六种状态；`risk_level` 是智能体判定的当前风险等级（-1 表示尚未判定）；`reject_reason` 存驳回/阻断原因（含违规片段与修改建议，直接展示给创作者） |
| **biz_category** | 稿件分类 | 如 生活家居 / 美妆护肤 |
| **biz_tag** | 标签 | 一篇文章可打多个标签，`name` 唯一 |
| **biz_article_tag** | 稿件与标签的多对多关系 | 联合唯一索引防重复 |
| **biz_report** | 举报记录 | 记录举报人、理由、处理状态与处理意见；举报成立会触发智能体复审 |

### 审核与适配（为智能体预埋，阶段 5 起使用）

| 表 | 存什么 | 关键字段与说明 |
|---|---|---|
| **audit_platform** | 目标平台清单 + 格式约束 | 每个平台带 `title_max_len`、`content_max_len`、`tag_rule`、`style_desc` —— 这是跨平台适配的规则依据。约束数值已于 2026-10-19 按各平台公开规范核对（微博 2000、B站按视频投稿等） |
| **audit_rule** | 审核规则库（RAG 检索的知识来源） | `rule_code` 如 AD-003（判定理由里会引用它，便于溯源）；`category` 六类；`platform_id` 空 = 通用规则；`source` 记录法规或规范来源，答辩要能说清依据 |
| **audit_record** | 智能体的每一次判定 | 记录触发场景（预检/审核/复审/适配预检）、风险等级、判定理由、命中规则、违规片段、处置建议，以及 `model_name`、`prompt_tokens`、`completion_tokens`、`duration_ms` —— 后四项是论文对比实验的成本与性能数据来源。`content_hash` 保存判定时的稿件内容指纹，用于判断结论是否已过期 |
| **audit_review** | 审核员的复核与改判 | `action`：1 采纳 / 2 改判 / 3 人工判定（无可用初判）；`remark` 记录原因（**改判必填**）。这是人机协同的闭环，也是最真实的评测标注数据 |
| **audit_sensitive_word** | 敏感词库 | 传统关键词匹配方案，**作为论文对比实验的基线**。词库为示意性质，不含真实攻击性词汇 |
| **audit_adaptation** | 跨平台适配产物 | 一篇稿件适配到某平台后的标题、正文、话题标签，以及格式自检与合规预检结论；`version` 记录同一稿件在同一平台的第几次适配（历史可回溯） |

## 五、与后续阶段的衔接

- **阶段 2**（RBAC 完整实现）：本阶段建好的 `sys_*` 五张表直接支撑用户、角色、菜单三个管理页面
- **阶段 3**（内容管理）：`biz_*` 五张表直接使用；稿件状态机与举报流程在此落地
- **阶段 5～6**（智能体）：`audit_*` 六张表预埋完毕，Agent 只需按既定契约读写，**不需要改表结构**
- **阶段 7**（评测实验）：`audit_record` 与 `audit_review` 已包含模型名、token 消耗、耗时与人工改判数据，实验所需数据从系统运行中自然积累

## 六、已知的不足（主动记录，答辩被问到不会慌）

1. 平台格式约束数值待核对（见上文说明）
2. 未建外键约束（取舍已说明）
3. 稿件与标签、审核记录与规则之间目前用字符串（逗号分隔 / JSON 字符串）保存关联，未做关联表或 JSON 类型字段 —— 取舍是"结构简单、便于人工查看"，数据量增大后可以优化
4. 未做分库分表、读写分离等 —— 本项目为单机规模，不需要
